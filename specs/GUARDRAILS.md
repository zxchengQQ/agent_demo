# 通用边界守卫规则 (General Guardrails)

> **定位**：本文档是项目所有开发技能的统一行为约束参照。每个 Skill 通过其"边界守卫 (Guardrails)"章节引用本文档中的对应阶段规则。
> **约束分级**：🔴 强制 (MUST) / 🟡 尽量 (SHOULD) / 🟢 建议 (RECOMMENDED) / ⚪ 可覆盖 (CONFIGURABLE)
> **项目基线**：agent-demo（Java 17 + Spring Boot 3.2.5 + LangChain4j + Vue 3）
> **关联文档**：`specs/SDD-工程业务背景文档.md`（业务约束）、`specs/SDD-项目技术指南文档.md`（技术约束）、`KNOWLEDGE_BASE.md`（项目知识库）

---

## 1. 阶段总览

| 阶段编号 | 阶段名称 | 对应 Skill | 核心产出 | 质量门禁 |
|:---|:---|:---|:---|:---|
| P0 | 项目基础建设阶段 |（元阶段，无独立 Skill）| 脚手架/配置/项目初始化 | 基础结构验证通过 |
| P1 | 需求分析阶段 | feature-requirements-clarification | 功能需求说明书（含 AC） | AC 评审通过 |
| P2 | 架构与设计阶段 | feature-tech-design | 技术方案文档 | 方案评审通过 |
| P3 | 规划与管理阶段 | feature-task-planning | 开发任务规划 | 任务规划确认 |
| P4 | 编码实现阶段 | feature-implementation | 可运行代码 + 测试 | 编译+测试通过 |
| P5 | 变更管理阶段 | feature-evolution | 增量任务计划 | 变更影响分析通过 |

> **说明**：P0 为元阶段，仅在项目初始化或重大基础设施重构时触发，不纳入常规迭代流水线。P1-P5 构成标准功能迭代闭环。

## 2. 通用规则（全阶段适用）

### 2.1 文档纪律

- 🔴 **文档先行**：进入下一阶段前，当前阶段的强制产出文档必须完成并确认。
- 🔴 **单一事实来源**：同一信息不得在多处重复定义。业务规则在 `SDD-工程业务背景文档.md` 定义，技术约束在 `SDD-项目技术指南文档.md` 定义。
- 🔴 **AI 编码约束引用**：AI Agent 的编码行为约束定义于 `SDD-项目技术指南文档.md` 第 4 节（TC-AI 系列），GUARDRAILS.md 不再重复定义，各阶段直接引用。
- 🟡 **引用而非复制**：跨文档引用时使用链接，禁止复制粘贴导致信息不一致。
- 🟢 **变更追溯**：所有文档变更必须记录变更日志（含 CR 编号、日期、变更原因和内容摘要）。

### 2.2 编号规范

编号规范与项目已有文档体系保持一致：

| 编号类型 | 格式 | 示例 | 范围 | 管理文档 |
|:---|:---|:---|:---|:---|
| AC | `AC-{3位序号}` | AC-001 | 功能范围内唯一 | 功能需求说明书 |
| BR | `BR-{模块缩写}-{3位序号}` | BR-LLM-001 | 项目范围内唯一 | SDD-工程业务背景文档 |
| TC | `TC-{类别缩写}-{3位序号}` | TC-LANG-001 | 项目范围内唯一 | SDD-项目技术指南文档 |
| CR | `CR-{3位序号}` | CR-001 | 按功能递增 | 变更日志 |
| Task | `Task-{2位序号}` | Task-01 | 按功能递增 | 任务规划文档 |

**模块缩写参考**：LLM（LLM 接入）、AGT（Agent 编排）、TOOL（工具调用）、MEM（记忆与会话）、SEC（安全合规）、ERR（错误码）、FE（前端对话）、LANG（Java 语言）、FRAMEWORK（框架）、LC4J（LangChain4j）、ORM（数据访问）、DB（数据库）、NAME（命名规范）、MVN（Maven 构建）、AI（AI 开发规范）

### 2.3 质量门禁

- 🔴 **门禁 P1→P2**：功能需求文档必须包含完整的 AC（覆盖正常、边界、异常三类场景），且 AC 使用 Given-When-Then 格式。
- 🔴 **门禁 P2→P3**：技术方案必须覆盖所有 AC，且 API 设计、数据库设计、核心逻辑三项齐全。
- 🔴 **门禁 P3→P4**：任务规划必须包含验证标准，且依赖关系清晰。
- 🔴 **门禁 P4→下一功能**：后端模块必须 `mvn compile -pl {模块名} -am` 编译通过；前端模块必须 `npm run test`（vitest）全部通过；无阻塞性 lint 或类型错误。
- 🟡 **门禁 P5→编码**：变更影响分析完成后，用户确认变更范围。

### 2.4 冲突处理

- 🔴 **规则冲突**：当本文件中不同阶段的规则冲突时，以后续阶段（编号更大）为准。
- 🔴 **阶段内规则优先**：阶段详细规则（第 3 节）优先于通用规则（第 2 节）。
- 🔴 **SDD 约束优先**：`SDD-工程业务背景文档.md` 中的 BR 约束和 `SDD-项目技术指南文档.md` 中的 TC 约束是项目真理源，与 GUARDRAILS.md 冲突时以 SDD 为准。
- 🟢 **紧急通道**：本项目的学习/演示性质，紧急修复可跳过阶段流程，但事后 24 小时内必须补齐缺失文档。紧急修复仅限演示/课程环境突发阻塞问题。
- 🟡 **规则覆盖**：任何规则的例外情况，必须经项目负责人确认并在对应文档中记录。

## 3. 阶段详细规则

### 3.0 P0：项目基础建设阶段（元阶段）

**触发场景**：项目初始化搭建、脚手架创建、基础设施重构、CI/CD 配置、根工程结构变更。

**适用 Skill**: 无独立 Skill。此阶段由项目治理架构师（Project Governance Architect）或项目负责人直接执行。

#### 入口条件
- [ ] 项目仓库已创建（git init / clone）
- [ ] 基础技术栈已选定（Java 17、Spring Boot、LangChain4j 等）

#### 强制产出物
- 🔴 多模块 Maven 工程骨架（根 POM + 子模块声明）
- 🔴 `agent-demo-bom` BOM 模块（第三方依赖版本统一管理）
- 🔴 `KNOWLEDGE_BASE.md` — 项目知识库（首次初始化）
- 🔴 `specs/SDD-工程业务背景文档.md` — 业务真理源
- 🔴 `specs/SDD-项目技术指南文档.md` — 技术真理源
- 🔴 TOGAF 架构文档（业务架构/技术架构/数据架构）
- 🔴 模块级业务说明书（`specs/modules/`）
- 🔴 AI 开发技能文件（`.agents/skills/`）
- 🟡 开发环境配置（`application-dev.yml` / `application-prod.yml`）
- 🟡 启动脚本（`start.ps1`）

#### 禁止事项
- 🔴 **禁止在此阶段讨论具体功能的业务逻辑**：只关注工程结构和项目治理。
- 🔴 **禁止在此阶段编写业务代码**（Controller / Service / Agent 实现等）。
- 🔴 **禁止在此阶段引入具体功能的第三方依赖**（基础设施工具除外）。
- 🟡 **禁止在此阶段配置业务相关属性**（如 Agent 提示词、模型路由等）。
- 🟢 **禁止跳过知识库建设**：`KNOWLEDGE_BASE.md` 是后续所有 AI 开发的前置依赖。

#### 允许事项
- ✅ 配置 Maven 多模块结构、BOM 版本管理
- ✅ 创建基础包结构（`com.agentdemo.*`）
- ✅ 定义公共组件（常量、枚举、异常体系、统一返回结果）
- ✅ 生成 AI 开发技能文件
- ✅ 建立 specs/ 文档体系框架

### 3.1 P1：需求分析阶段

**适用 Skill**: feature-requirements-clarification

#### 入口条件
- [ ] 用户有一个待开发的功能想法或项目愿景

#### 强制产出物
- 🔴 `specs/features/{yyyy-MM-dd}/{功能名}/{功能名}.md` — 功能需求说明书
- 🔴 验收标准（AC）清单，覆盖正常流程、边界情况、异常处理三类场景
- 🟡 用户故事与 AC 的对应关系表

#### 禁止事项
- 🔴 **禁止讨论数据库表结构、API 接口定义、代码实现细节**
- 🔴 **禁止在 AC 中使用非 Given-When-Then 格式**
- 🟡 **禁止跳过场景覆盖**：AC 必须覆盖正常流程、边界情况、异常处理三类场景，缺少任一类别需补问
- 🟡 **禁止使用技术术语描述业务需求**（如"JSON"、"API"、"Table" 等）
- 🟢 **禁止代替用户做需求决策**：当用户意图不明确时，必须通过引导式提问确认

#### 允许事项
- ✅ 使用业务术语描述用户操作流程
- ✅ 使用非技术语言（"用户"、"页面"、"流程"）
- ✅ 通过引导式提问逐步收敛需求

---

### 3.2 P2：架构与设计阶段

**适用 Skill**: feature-tech-design

#### 入口条件
- [ ] `specs/features/{yyyy-MM-dd}/{功能名}/{功能名}.md` 已存在且包含完整 AC
- [ ] 项目技术栈和结构规则已明确（参考 `SDD-项目技术指南文档.md`）

#### 强制产出物
- 🔴 `specs/features/{yyyy-MM-dd}/{功能名}/{功能名}_技术方案.md` — 技术方案文档
- 🔴 API 接口定义（路径、参数、请求/响应格式）
- 🔴 核心类设计（类名、职责、关键方法）
- 🔴 验收标准映射表（每个 AC 对应到具体技术实现点）
- 🟡 数据库设计（表结构、索引、约束）—— 如涉及持久化
- 🟡 Mermaid 流程图或时序图（核心流程）

#### 禁止事项
- 🔴 **禁止在未确认需求文档的情况下开始设计**
- 🔴 **禁止遗漏任何验收标准的实现方案**：每个 AC 必须有对应的技术实现
- 🟡 **禁止在方案中出现"待定"或"后续再说"**：设计必须可落地
- 🟡 **禁止引入未经评估的新技术依赖**：必须在方案中评估兼容性和版本约束
- 🟢 **禁止只描述正常流程**：必须同时设计异常处理和边界条件

#### 允许事项
- ✅ 使用 Mermaid 图表表示架构和流程
- ✅ 多种方案对比并给出推荐
- ✅ 引用项目已有实现范式（参考 `SDD-项目技术指南文档.md` 第 4.4 节）

---

### 3.3 P3：规划与管理阶段

**适用 Skill**: feature-task-planning

#### 入口条件
- [ ] `specs/features/{yyyy-MM-dd}/{功能名}/{功能名}_技术方案.md` 已存在且完整
- [ ] 技术方案中的验收标准映射表完整

#### 强制产出物
- 🔴 `specs/features/{yyyy-MM-dd}/{功能名}/{功能名}_任务规划.md` — 任务规划文档
- 🔴 每个任务包含通俗解释、涉及文件和验证标准
- 🔴 任务依赖关系图（Mermaid）
- 🟡 工时估算
- 🟡 风险任务和阻塞任务标注

#### 禁止事项
- 🔴 **禁止将"编写单元测试"作为独立任务规划**（测试在每个任务的 TDD 循环中完成）
- 🔴 **禁止任务粒度超出原子范围**（每个任务单一职责，< 0.1 天）
- 🟡 **禁止任务规划中没有验证标准**
- 🟡 **禁止缺少通俗解释字段**
- 🟢 **禁止忽略 Mock 对接闭环**：存在 Mock 时必须规划对接真实接口的任务

#### 允许事项
- ✅ 将大任务拆分为可并行的小任务
- ✅ 使用分层顺序组织任务（数据层→表现层→业务逻辑层→接口对接层→异常处理与优化）

---

### 3.4 P4：编码实现阶段

**适用 Skill**: feature-implementation

**内部子循环**：每个任务内部遵循 TDD 微循环（RED → GREEN → REFACTOR），详见各 Skill 内部定义。

#### 入口条件
- [ ] `specs/features/{yyyy-MM-dd}/{功能名}/{功能名}_任务规划.md` 已存在
- [ ] 前置阶段的依赖任务已完成

#### 强制产出物
- 🔴 可运行的实现代码
- 🔴 对应的测试代码（TDD RED 阶段产出的失败测试 → GREEN 阶段使其通过）
- 🔴 更新后的任务规划文档（任务状态已勾选）

#### 禁止事项
- 🔴 **禁止跳过 RED 阶段直接写实现代码**（TDD 铁律）
- 🔴 **禁止写没有失败测试的实现代码**
- 🔴 **禁止写超出当前测试范围的代码**（只写让当前测试通过的最少代码）
- 🔴 **禁止提交未通过编译的代码**：必须 `mvn compile -pl {模块名} -am` 验证
- 🟡 **禁止一次性完成所有阶段**：每次只执行用户指定的阶段
- 🟡 **禁止在未确认依赖任务完成的情况下开始任务**
- 🟢 **禁止跳过验收测试闭环**：TDD 循环完成后必须执行验收测试

#### 允许事项
- ✅ 在测试保护下重构代码
- ✅ 复用项目中已有的代码、组件、工具函数
- ✅ 发现文档不一致时同步更新文档
- ✅ 编译验证通过后提交代码

---

### 3.5 P5：变更管理阶段

**适用 Skill**: feature-evolution

#### 入口条件
- [ ] 存在已有功能的完整文档（需求 + 技术方案 + 任务规划）
- [ ] 已完成的编码实现

#### 强制产出物
- 🔴 增量任务计划：`{功能名}_变更任务_{CR序号}.md`
- 🟡 变更影响分析报告（内嵌在任务计划中）
- 🟡 更新后的需求文档/技术方案（如需）

#### 禁止事项
- 🔴 **禁止编写、修改或输出任何实际业务代码**
- 🔴 **禁止整体推倒重写已有文档**（采用"就地修改 + 变更日志"方式）
- 🟡 **禁止删除或重写已通过验证的任务和代码**
- 🟡 **禁止在未完成变更分类的情况下直接修改文档**
- 🟢 **禁止忽略回归验证**：必须规划回归验证任务

#### 允许事项
- ✅ 就地修改已有文档正文
- ✅ 在文档末尾追加变更日志
- ✅ 生成仅限于变更部分的增量任务

## 4. 决策权限矩阵

| 决策类型 | 决策者 | 说明 |
|:---|:---|:---|
| 需求范围界定 | 产品经理 / 项目负责人 | 确定功能的边界和优先级 |
| 需求变更（新增/修改 AC） | 产品经理 / 项目负责人 | 需评估影响后确认 |
| 技术方案选择 | 系统架构师 / Tech Lead | 有多种方案时给出推荐 |
| 技术变更（影响接口/模块边界） | 系统架构师 + Tech Lead | 需评估兼容性和回归影响 |
| 任务拆解和排期 | Tech Lead | 确定任务粒度和执行顺序 |
| 编码实现细节 | 开发工程师 | 在技术方案范围内自主决策 |
| 选择与引入新技术依赖 | 系统架构师 | 需评估版本兼容性（参考 BOM 约束） |
| 紧急修复 | 开发工程师 + Tech Lead | 事后勤补文档 |
| 文档变更 | AI Agent / 任务执行者 | 遵循变更日志规范 |
| AI 编码行为约束豁免 | 项目负责人 | 需在对应文档中记录豁免原因 |

> **说明**：本项目为学习示例项目，部分角色（产品经理/架构师）可能由项目负责人兼任。
