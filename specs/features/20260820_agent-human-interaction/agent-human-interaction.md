## 1. 背景与价值 (Context & Value)

*   **背景**: agent-demo 项目已实现单 Agent ReAct 对话、工具调用、RAG 知识库、MCP 协议、多 Agent 编排和工作流编排等能力，但 Agent 在任务执行过程中遇到歧义或需执行关键操作时，缺乏向用户提问/确认的机制，只能盲目猜测或直接执行，存在误操作风险和用户体验问题。
*   **目标**: 为单 Agent ReAct 对话增加 Human-in-the-Loop (HITL) 交互能力，使 Agent 在遇到歧义或需执行有副作用的操作时，能主动向用户提问/确认，等待用户回复后继续执行。
*   **关联**: 本期为单 Agent 对话澄清能力，后续将扩展至工作流编排 HITL。

## 2. Agent 角色定义 (Agent Persona)

### 2.1 身份定位

*   **角色名称**: Agent-Human 交互能力（非独立 Agent，是现有单 Agent 的能力增强）
*   **角色类型**: 混合型（对话澄清 + 任务确认）
*   **身份描述**: Agent 在执行任务过程中的"提问者"角色，当遇到信息不完整或需确认关键操作时，主动向用户发起交互
*   **核心价值**: 避免 Agent 盲目猜测导致错误执行，避免有副作用的操作未经确认就执行，提升用户对 Agent 行为的掌控感和信任度

### 2.2 目标用户与场景

*   **目标用户**: agent-demo 的学习者、开发者、API 调用方
*   **使用场景**:
    *   用户指令存在歧义（如"帮我查订单"但未提供订单号）时，Agent 追问必要参数
    *   Agent 即将执行有副作用的操作（如删除文件、修改数据、发送请求）前，向用户确认
    *   用户指令面临多种可选方案时，Agent 请用户选择
*   **交互风格**: 简洁直接，主动提问，提供选项引导

## 3. 能力边界与自主性 (Capability & Autonomy)

### 3.1 能力清单（In Scope）

*   **歧义澄清**: 用户指令缺少必要参数、存在歧义、或面临多种可选方案时，Agent 主动追问
*   **关键操作确认**: Agent 即将执行有副作用的操作前，向用户发起确认
*   **异步暂停-恢复**: Agent 调用提问工具后暂停执行，保存"等待用户输入"状态，用户回复后从暂停点恢复
*   **多轮追问**: 用户回复仍模糊时，Agent 最多追问 3 次，每次提供选项引导
*   **混合交互形式**: 开放式追问用纯文本，确认型交互用结构化卡片（含按钮）

### 3.2 能力禁区（Out of Scope）

*   **工作流 HITL** - 本期不实现，后续扩展至工作流编排系统的关键节点人工确认
*   **超时降级机制** - 本期不实现独立的提问超时策略，复用现有会话超时（30 分钟）自然清理
*   **提示注入防护** - 本期不实现，用户回复视为可信输入，与现有对话流安全级别一致
*   **长期记忆** - 本期不实现跨会话的澄清历史记忆

### 3.3 自主性级别

*   **级别**: L2 - 确认后执行
*   **说明**: Agent 在遇到歧义时主动追问澄清，在执行有副作用的操作前向用户确认，用户确认后才执行。常规无副作用操作（如查询、计算）Agent 自主推进，不打断用户。
*   **人类介入点**:
    *   歧义澄清：Agent 缺少必要信息无法继续时
    *   关键操作确认：Agent 即将执行有副作用的操作时
    *   追问超限：Agent 追问 3 次后仍无法获得有效信息时，终止任务并告知用户

### 3.4 知识边界

*   **知识范围**: 依赖现有 Agent 的知识范围（由系统提示词和工具能力决定）
*   **超出边界处理**: 当用户请求超出 Agent 能力时，Agent 应告知用户无法处理的原因，并建议可能的替代方案

## 4. 工具与动作空间 (Tools & Action Space)

### 4.1 工具清单

| 工具名称 | 用途 | 输入 | 输出 | 副作用 | 权限 | 限制 | 常见失败场景 |
|---------|------|------|------|--------|------|------|-------------|
| askUser | 向用户发起提问/确认 | type（text/confirm）、question（问题文本）、options（选项列表，confirm 类型必填） | 用户回复文本 | 无（仅暂停 Agent 执行） | 只读（不修改任何系统状态） | 同一问题最多追问 3 次；同一会话同一时间只能有一个等待中的提问 | 用户长时间不回复（依赖会话超时清理） |

### 4.2 工具间关系

*   **依赖关系**: askUser 工具的输出（用户回复）作为 Agent 后续推理的上下文输入
*   **互斥关系**: askUser 与其他工具不能在同一 ReAct 步骤中同时调用（askUser 会暂停 Agent 执行）
*   **编排策略**: Agent 在 ReAct 循环中，当识别到需要澄清/确认时，调用 askUser 工具暂停执行；用户回复后，Agent 继续 ReAct 循环，可能调用其他工具完成后续任务

### 4.3 工具选择策略

*   Agent 通过 ReAct 推理自主判断是否需要调用 askUser 工具
*   开放式追问（如缺少参数）使用 type=text，用户通过输入框回复
*   确认型交互（如关键操作确认）使用 type=confirm，携带选项列表，用户通过点击按钮回复
*   无副作用的查询/计算操作无需确认，Agent 直接执行

## 5. 推理流程与记忆策略 (Reasoning & Memory)

### 5.1 推理模式

*   **主要模式**: ReAct（推理-行动），与现有单 Agent 架构一致
*   **模式选择策略**: 不改变现有推理模式，askUser 作为一个工具嵌入 ReAct 循环
*   **最大执行步骤**: 受现有 `agent.max-iterations=10` 约束，askUser 调用不计入迭代次数（暂停状态不消耗迭代）

### 5.2 澄清策略

*   **主动澄清条件**:
    *   用户指令缺少执行任务所需的必要参数
    *   用户指令存在歧义，有多种可能的理解
    *   Agent 即将执行有副作用的操作（删除、修改、发送等）
*   **自主推进条件**:
    *   无副作用的查询/计算操作
    *   用户指令明确、参数完整
    *   Agent 有足够信息自主决策
*   **最大澄清轮次**: 同一问题最多追问 3 次，每次应提供具体选项引导用户；3 次后终止任务并告知用户

### 5.3 短期记忆（对话内）

*   **上下文保留轮次**: 复用现有短期记忆窗口（20 条消息），跨暂停-恢复周期保持完整上下文
*   **上下文溢出处理**: 复用现有 FIFO 淘汰策略，最早的 Q&A 对可能被淘汰

### 5.4 长期记忆（跨会话）

*   **是否需要**: 否
*   **记忆内容**: 不适用
*   **遗忘策略**: 不适用

## 6. 护栏安全与降级策略 (Guardrails & Fallback)

### 6.1 内容安全规则

*   **必须拒绝的请求**: 继承现有 Agent 的内容安全规则
*   **标准拒绝话术**: 继承现有 Agent 的拒绝话术
*   **敏感话题处理**: 继承现有 Agent 的处理策略

### 6.2 幻觉防护

*   **回答依据**: 继承现有 Agent 策略（可基于自身知识 + 工具/知识库数据）
*   **无结果处理**: Agent 应如实告知用户无法获取相关信息，不编造内容

### 6.3 敏感信息处理

*   **输入侧**: 用户回复视为可信输入，与现有对话流安全级别一致
*   **输出侧**: Agent 提问内容不应包含不必要的敏感信息

### 6.4 工具失败降级

| 工具 | 失败场景 | 降级策略 | 是否转人工 |
|------|---------|---------|-----------|
| askUser | 用户长时间不回复 | 依赖会话超时（30 分钟）自然清理等待状态，用户下次消息创建新会话 | 否 |
| askUser | 用户回复仍然模糊/无效 | 最多追问 3 次，每次提供选项引导；3 次后终止当前任务并告知用户 | 否 |
| askUser | 用户取消（发送"取消"或点击取消按钮） | Agent 停止当前任务，确认取消并准备接收新指令 | 否 |

### 6.5 人机协作机制

*   **升级条件**: Agent 经过用户澄清后仍无法完成任务（如工具失败、能力超出边界）
*   **升级方式**: Agent 直接告知用户无法继续的原因和建议的后续步骤（无人工转接机制，本项目为学习示例）
*   **交接信息**: Agent 应提供当前任务状态、已尝试的方案、失败原因

### 6.6 提示注入防护

*   **攻击识别**: 本期不实现提示注入检测，用户回复视为可信输入
*   **处理策略**: 与现有对话流安全级别一致（本项目为学习示例，无认证机制）
*   **工具返回防护**: 不适用（askUser 工具返回的是用户回复，非外部系统数据）

### 6.7 权限与身份校验

*   **身份确认机制**: 继承项目现有策略（无认证机制，学习示例工程）
*   **防越权策略**: 继承项目现有策略（会话隔离按 sessionId）
*   **数据隔离**: 会话级隔离，Agent 的等待状态按 sessionId 隔离，不同会话互不影响

## 7. 验收标准 (Acceptance Criteria)

> **重要**：以下验收标准是后续 Prompt 工程、工具开发和评估测试的直接依据。每条 AC 使用 Given-When-Then 格式，Given 描述上下文/状态，When 描述触发条件，Then 描述预期行为。AI Agent 的 AC 关注**行为约束**而非精确输出。

### 7.1 正常交互流程 (Normal Interaction)

- [ ] **AC-N01**: 歧义检测与主动追问
    - Given: 用户发送包含歧义意图的消息（如"帮我查订单"但未提供订单号），Agent 处于正常 ReAct 对话状态
    - When: Agent 在 ReAct 推理中识别到缺少执行任务所需的必要信息
    - Then: Agent 应调用 askUser 工具发起追问，明确告知用户需要什么信息；Agent 不应在信息不完整时盲目推进任务或猜测参数

- [ ] **AC-N02**: 关键操作前确认
    - Given: Agent 即将执行有副作用的操作（如删除文件、修改数据、发送 HTTP 请求），Agent 处于正常 ReAct 对话状态
    - When: Agent 判定该操作有副作用，需要用户确认
    - Then: Agent 应调用 askUser 工具发起确认（type=confirm，携带确认/取消选项）；Agent 不应在未确认时执行有副作用的操作

- [ ] **AC-N03**: 用户回复后恢复执行
    - Given: Agent 处于"等待用户输入"暂停状态，用户收到 Agent 的提问
    - When: 用户发送回复消息（CR-001：回复后该消息不产生独立用户气泡，由交互卡片锁定态展示答案）
    - Then: Agent 应从暂停点恢复执行，将用户回复作为上下文继续 ReAct 循环；Agent 应保留之前对话的完整上下文（包括提问内容和用户的回复）；Agent 恢复后生成的输出应在**同一对话气泡**（含提问/交互卡片的气泡）内继续展示，不应新启独立助手气泡

- [ ] **AC-N04**: HITL 决策后同气泡续写（CR-001 新增）
    - Given: Agent 已发起 HITL 交互（如确认卡片 ConfirmCard 的批准/拒绝，或 AskUserCard 的选项/文本回复），用户完成了决策或回复
    - When: Agent 从暂停点恢复执行并生成后续输出（流式 token）
    - Then: 后续输出应在**含该交互卡片/问题的同一助手气泡**内继续展示，让用户明确这是对同一对话问题的延续，而非新一轮对话；不应新启独立助手气泡，也不应改变交互卡片的锁定态展示。**CR-002：交互卡片内嵌于该气泡的 ReAct 推理过程区块内对应工具调用步骤处展示（而非气泡底部）。CR-003：同一气泡内可连续发生多次交互（多次审批/追问），每次交互记录独立保留，互不覆盖**

- [ ] **AC-N05**: HITL 推理过程区块保持展开（CR-002 新增）
    - Given: 某助手消息的 ReAct 推理过程区块内包含 HITL 交互卡片（AskUserCard/ConfirmCard），消息处于"等待用户输入"暂停态或已完成续写
    - When: 用户查看该消息，或消息状态从 incomplete 变为 complete（流式结束）
    - Then: 该消息的 ReAct 推理过程区块应保持展开，交互卡片始终可见（等待态下可交互，完成后可回看锁定态）；不应因区块默认折叠导致卡片被隐藏而无法交互或回看；不含 HITL 卡片的普通消息维持原折叠语义

- [ ] **AC-N06**: 多次审批/追问记录保留（CR-003 新增）
    - Given: 同一助手气泡内 Agent 连续发起多次 HITL 交互（如多次工具权限审批：工具A确认→批准→续跑→工具B确认→…；或多次 askUser 追问），`message.askUserData` 已由单对象扩展为"当前镜像 + 历史记录数组"
    - When: 用户逐一批准/拒绝或回复每次交互
    - Then: 每次交互的记录（工具名/问题/参数 + 决策 approved/answer）均被保留，并各自内嵌展示于对应工具调用步骤处，带各自锁定态可回看；不应只保留最后一次交互记录，也不应因新交互到来而覆盖/丢失此前已完成的审批记录

### 7.2 工具选择与调用 (Tool Selection & Invocation)

- [ ] **AC-T01**: 开放式追问使用纯文本形式
    - Given: Agent 需要问一个开放式问题（如"订单号是多少？"），用户需要自由输入回复
    - When: Agent 调用 askUser 工具，type=text
    - Then: 前端应将问题作为普通助手消息展示在对话流中；用户应通过现有输入框自由输入回复；前端不应展示额外的按钮或表单

- [ ] **AC-T02**: 确认型交互使用结构化卡片
    - Given: Agent 需要确认一个关键操作（如"确认删除文件 XXX？"），用户需要选择确认或取消
    - When: Agent 调用 askUser 工具，type=confirm，携带选项列表（如 ["确认", "取消"]）
    - Then: 前端应展示结构化卡片（问题文本 + 选项按钮）；用户应通过点击按钮回复；前端不应允许通过输入框文本绕过按钮选择

### 7.3 安全与护栏 (Safety & Guardrails)

- [ ] **AC-S01**: 追问次数上限
    - Given: Agent 已对同一问题追问 3 次，用户每次的回复仍然模糊或无效
    - When: Agent 达到第 3 次追问上限
    - Then: Agent 应终止当前任务并明确告知用户"由于信息不完整，无法继续执行该任务"；Agent 不应继续追问同一问题；Agent 应准备好接收新的用户指令

- [ ] **AC-S02**: 追问时提供选项引导
    - Given: Agent 因用户回复模糊而需要重新追问同一问题
    - When: Agent 发起追问
    - Then: Agent 应在追问时提供具体可选项或示例帮助用户理解需要什么信息（如"请提供订单号，例如：ORD-12345"）；Agent 不应简单重复原始问题文本

### 7.4 边界与降级 (Edge Cases & Fallback)

- [ ] **AC-E01**: 会话超时清理等待状态
    - Given: Agent 处于"等待用户输入"暂停状态，30 分钟内用户未发送任何回复
    - When: 会话超时清理定时任务执行（每 5 分钟扫描一次）
    - Then: Agent 的等待状态应随会话一起被清理；用户下次发送消息时应创建新会话开始新对话；不应残留过期的等待状态

- [ ] **AC-E02**: 用户在等待期间切换话题
    - Given: Agent 正在等待用户对澄清问题的回复，Agent 处于"等待用户输入"状态
    - When: 用户发送了一条与当前澄清问题完全无关的消息（如 Agent 在问订单号，用户却问了天气）
    - Then: Agent 应识别话题切换；Agent 应询问用户是否要放弃当前任务转而处理新话题；Agent 不应忽略用户的新消息也不应在新话题上丢失之前的任务上下文

### 7.5 记忆与上下文 (Memory & Context)

- [ ] **AC-M01**: 跨暂停-恢复的上下文保持
    - Given: Agent 在任务执行中途暂停提问，对话历史中包含之前的交互记录
    - When: 用户回复后 Agent 恢复执行
    - Then: Agent 应能访问完整对话历史（包括之前的所有消息、提问和回答）；Agent 应将用户回复整合到后续推理中；Agent 不应因暂停-恢复而丢失任何上下文

- [ ] **AC-M02**: 连续多轮澄清的上下文连续性
    - Given: Agent 在单个任务中需要连续提问多个问题（如先问订单号，再问物流方式）
    - When: Agent 收到第一个问题的回复后需要追问第二个问题
    - Then: Agent 应保持前后 Q&A 对的上下文连续性；Agent 不应丢失之前已澄清的信息；Agent 应基于已有信息继续推进任务

### 7.6 人机协作 (Human-in-the-Loop)

- [ ] **AC-H01**: 任务无法完成时的告知
    - Given: Agent 即使经过用户澄清仍无法完成任务（如工具调用失败、能力超出边界）
    - When: Agent 判定无法继续执行
    - Then: Agent 应明确告知用户无法继续的具体原因；Agent 应建议可能的后续步骤（如重试、更换方案、检查参数）；Agent 不应静默放弃或无限重试

- [ ] **AC-H02**: 用户主动取消等待中的澄清
    - Given: Agent 正在等待用户回复澄清问题，Agent 处于"等待用户输入"状态
    - When: 用户明确表示取消（如发送"取消"文本，或点击结构化卡片的"取消"按钮）
    - Then: Agent 应停止当前任务；Agent 应确认取消并告知用户已取消；Agent 应准备好接收新的用户指令

## 8. 范围界定 (Scope)

### 8.1 本次范围（In Scope）

*   **askUser 工具**: 新增"向用户提问"工具，支持 text（纯文本追问）和 confirm（结构化确认卡片）两种类型
*   **异步暂停-恢复机制**: Agent 调用 askUser 后暂停执行并保存状态，用户回复后从暂停点恢复，按 sessionId 隔离
*   **SSE 事件扩展**: 新增 SSE 事件类型，支持向前端推送"提问"事件（含问题文本、类型、选项）
*   **前端交互 UI**: 
    *   纯文本追问：复用现有对话消息展示
    *   结构化确认卡片：新增确认卡片组件（问题文本 + 选项按钮）
*   **追问策略**: 最多 3 次 + 选项引导，超限终止任务
*   **会话状态管理**: "等待用户输入"状态的保存、恢复、清理（复用会话超时机制）

### 8.2 不在本次范围（Out of Scope）

*   **工作流编排 HITL** - 下一期扩展，将 askUser 机制集成到工作流的 PAUSED 状态和断点恢复流程中
*   **超时降级机制** - 本期复用会话超时（30 分钟）自然清理，不实现独立的提问超时策略
*   **提示注入防护** - 本期信任用户回复，后续可增加关键词过滤和标记隔离
*   **长期记忆** - 本期不实现跨会话的澄清历史记忆
*   **多 Agent 协作 HITL** - 本期不涉及多 Agent 场景的人工介入

### 8.3 评估方式

*   **评估数据来源**: 手动测试场景（前端交互验证）+ 单元测试（后端状态管理、工具调用逻辑）
*   **自动/人工评估**:
    *   前端交互（卡片展示、按钮点击、文本追问）: 人工评估
    *   后端状态流转（暂停-恢复-清理）: 自动化单元测试
    *   工具调用逻辑（askUser 参数、追问计数）: 自动化单元测试
*   **通过标准**: 所有 AC 通过手动验证或自动化测试覆盖

## 变更日志 (Change Log)

### CR-001: HITL 恢复后续写同气泡展示 (2026-08-28)

**变更类型**: 能力扩展 (Capability Extension)
**变更原因**: 人机交互模式下，用户点击批准/拒绝或回复 HITL 交互后，前端会新启一个独立助手气泡展示续写内容，容易被用户误认为已开启新一轮对话；实际上仍是在处理同一个对话问题。希望恢复后的续写在同一个对话气泡内继续展示。
**变更内容摘要**:
- [新增] AC-N04: HITL 决策后同气泡续写——批准/拒绝（ConfirmCard）或选项回复（AskUserCard）后，续写输出在同一气泡（含交互卡片的气泡）内继续展示，不新启助手气泡
- [修改] AC-N03: 用户回复后恢复执行 → 补充约束：恢复后 Agent 的输出在同一对话气泡内继续展示，不新启助手气泡；且 askUser 文本/选项回复不再产生独立用户气泡（由卡片锁定态展示答案）
- [前端] ChatWindow.vue sendMessage 新增 HITL 恢复分支：复用最后一条含 HITL 卡片/问题的助手气泡作为流式目标；askUser 回复（handleAskUserReply）改为 silent 模式
- [前端] session.ts 新增恢复流式状态方法（复用气泡 status 置回 incomplete，续写后 markComplete）

### CR-002: HITL 交互卡片内嵌于 ReAct 推理过程区块 (2026-08-28)

**变更类型**: 能力扩展 (Capability Extension)
**变更原因**: CR-001 同气泡续写落地后，交互卡片（AskUserCard/ConfirmCard）仍展示在气泡底部（ask-user-block），与 ReAct 推理过程割裂。希望将卡片内嵌到 ReAct 推理过程区块内对应工具调用步骤处，让"Agent 推理到某一步 → 调用工具 → 此处交互"的语义更清晰。
**变更内容摘要**:
- [新增] AC-N05: HITL 推理过程区块保持展开——含 HITL 卡片的消息 react-block 恒展开，卡片始终可见可交互/可回看
- [修改] AC-N04: HITL 决策后同气泡续写 → 补充展示约束：交互卡片内嵌于 ReAct 推理过程区块内对应工具调用步骤处（而非气泡底部）
- [前端] MessageItem.vue：卡片-步骤关联（按 askUser / 权限工具 toolName 匹配对应工具卡片），react-block 内嵌渲染交互卡片；无匹配时回退底部 ask-user-block
- [前端] MessageItem.vue：折叠逻辑调整——含 HITL 卡片的消息 react-block 恒展开，其他消息维持原折叠语义

### CR-003: 多次审批/追问记录保留 (2026-08-28)

**变更类型**: 能力扩展 (Capability Extension)
**变更原因**: 多次审批/追问页面只保留最后一次记录——`message.askUserData` 为单对象，每次新的 tool_confirm/ask_user 事件覆盖上一次；CR-001 同气泡续写后多次审批复用同一气泡，导致此前已完成的审批记录（工具/参数 + 决策）丢失。希望多次审批记录逐一保留、可回看。
**变更内容摘要**:
- [新增] AC-N06: 多次审批/追问记录保留——每次交互记录独立保留，各自内嵌展示于对应工具步骤，可回看，互不覆盖
- [修改] AC-N04: HITL 决策后同气泡续写 → 补充"同一气泡内可连续多次交互，记录互不覆盖"
- [前端] 数据模型：`Message` 新增 `askUserHistory?: AskUserData[]`（历史记录数组），`askUserData` 保留为最新一条镜像（不破坏 isWaitingForUserInput / ChatWindow 恢复检测 / 兜底渲染）
- [前端] session.ts：setToolConfirmData/setAskUserData 改为"追加历史 + 同步镜像"；setToolConfirmApproved/setAskUserAnswer 改为"更新最后一条历史 + 同步镜像"
- [前端] MessageItem.vue：遍历 askUserHistory，每条记录内嵌到对应工具步骤（首个未占用匹配），无匹配兜底底部渲染
