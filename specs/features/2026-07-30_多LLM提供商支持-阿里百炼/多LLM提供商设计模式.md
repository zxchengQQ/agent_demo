# 多服务商接入架构设计（通用模式描述）

## 1. 要解决的问题

同一能力（模型调用/支付/短信）存在多家服务商，且：**新服务商接入频率高、每家协议不同、凭证敏感、切换不可影响核心系统**。目标：核心系统与具体服务商**零耦合**——"加一家服务商 = 加一个插件"，不改一行核心代码。

## 2. 总体设计原则（四句话）

1. **供应商代码不进核心进程**——独立运行环境（插件/子进程/容器），核心只做编排
2. **核心定"骨架"，供应商填"差异"**——统一抽象基类/协议，流程模板化
3. **核心永远不认识具体厂商**——通过注册表/工厂按名字取用，杜绝 import 厂商类
4. **凭证敏感信息集中管理**——加解密入库 + 缓存 + 租户隔离

## 3. 分层架构（五层）

```
┌ 接入层   Controller/API    —— 管理界面（列服务商、填凭证、测连通）
├ 编排层   ProviderManager   —— 服务商配置（哪些可用、默认哪家、凭证）
│         ModelManager       —— 实例工厂 + 默认实例 + 负载均衡
├ 契约层   抽象基类/协议       —— 定义"每个服务商必须实现什么"（骨架）
├ 桥接层   Runtime Adapter   —— 把"核心内部调用方式"翻译成"服务商执行环境的方式"
└ 执行层   供应商实现          —— 真实调用外部 API 的代码（隔离运行）
```

## 4. 逐层设计要点

### 契约层（最重要，先定义"长什么样"）

- 
  定义 **能力矩阵**：所有服务商共享的能力集合（如 LLM 场景：聊天/向量化/重排/审核…），每种能力 = 一个抽象基类
- 基类实现**通用流程**（凭证校验→调用→错误归一化→token 统计），子类只写差异
- 提供**能力→基类 的映射表**，运行时按能力取类
- 好处：新增"能力"只需加一个基类 + 各家补实现

### 编排层

- **点餐台**：`get_instance(tenant, provider, capability)` 统一入口——不指定 provider 时回退到租户默认
- **负载均衡**：同一服务商同能力多组凭证 → 轮询/加权策略（策略模式），单点失败自动切换
- **配置缓存**：服务商配置读多写少 → 短 TTL 缓存 + 变更失效

### 桥接层

- 契约层调用通过**适配器**翻译为执行环境的远程调用（HTTP/gRPC/消息）
- 适配器负责：身份校验（API Key）、流式响应转发、错误码映射（把厂商错误统一成内部错误类型）
- 可加**结构适配小对象**：只暴露调用方需要的最小方法面，隔离依赖

### 执行层

- 服务商代码独立部署（容器/子进程），故障隔离：**某家服务商挂了不影响核心**
- 热插拔：安装/卸载不重启核心

## 5. 设计模式清单（每项标好"什么时候用"）

| 模式                | 解决什么                               | 落地位置      |
| :------------------ | :------------------------------------- | :------------ |
| 抽象基类 + 模板方法 | 各家共享流程、只填差异                 | 契约层        |
| 工厂方法            | 统一入口造实例，调用方不知道细节       | 编排层        |
| 策略模式            | 能力分派、负载均衡算法可替换           | 编排层/契约层 |
| 注册表（服务定位）  | 按名字找到服务商定义，不 import 具体类 | 契约层        |
| 适配器              | 内部调用 ↔ 厂商执行环境 协议互译       | 桥接层        |
| 代理/桥接           | 远程执行、故障隔离                     | 桥接层+执行层 |
| 组合 + 惰性初始化   | 按需组装各管理器，避免循环依赖         | 编排层        |
| 缓存                | 高频读的配置/schema                    | 编排层        |

## 6. 落地清单（自检项）

- 核心代码能否做到 `import` 里**没有任何一个具体服务商类**？
- 新增一家服务商是否只需"写插件 + 装上去"，零核心改动？
- 凭证是否加密存储、按租户隔离、返回前脱敏？
- 服务商宕机是否只报错给本次请求，不影响其他服务商？
- 统一错误类型是否覆盖所有厂商（未配置/无权限/限流/超时）？
- 是否提供"连通性测试"入口（填完凭证点一下验证）？
- 协议是否支持流式（长响应边生成边转发）？

## 7. 适用与不适用

- **适用**：服务商数量 5+ 且持续增长、每家协议差异大、凭证敏感、需要隔离
- **不适用**：只有 1-2 家且稳定（抽象层是浪费）、调用频率极低、实时性要求使远程桥接不可接受（把执行层改为进程内插件即可）
