# 功能需求说明书 (Feature Requirements Document)

## 1. 背景与价值 (Context & Value)

*   **背景**: 项目当前已实现单 Agent 对话（SimpleAgent + ReAct 循环）、RAG 知识库问答、MCP 协议工具调用等核心能力，但缺乏多 Agent 协作和工作流编排能力。`agent-demo-app` 模块自项目创建以来一直为空模块（仅有 `pom.xml`），其定位为"应用编排层"，依赖 `agent`、`rag`、`mcp` 三个模块。现有 `PlanAgent` + `TaskBreakdownStream` 提供了任务拆解的雏形，但未形成通用的编排框架。
*   **目标**: 基于 LangChain4j 的 `langchain4j-agentic` 模块，构建一套通用的多 Agent 编排框架，让开发者能通过 Java 代码快速定义业务场景下的多 Agent 协作流程，并提供前端模板选择、执行可视化和独立 API 供用户使用。
*   **关联**: 能力矩阵中"多 Agent 协作"和"工作流编排"两项从"🚧 规划中"更新为"✅ 已实现"；`AgentType` 枚举中 `MULTI` 和 `WORKFLOW` 状态启用。
*   **技术路线**: 引入 `langchain4j-agentic:1.17.2-beta27` 作为编排引擎，`agent-demo-app` 作为适配层桥接项目已有的 `LlmConfigStore`、`ToolRegistry`、`PromptTemplateLoader`、`SessionManager` 等能力，不重复造轮子。

## 2. 功能范围 (Scope)

### 2.1 总体范围（Full Vision）

以下为应用编排层的完整能力愿景，将分三阶段实现（见 2.2 节）：

*   **基础适配层**: 引入 `langchain4j-agentic` 依赖，实现与 `LlmConfigStore`/`ModelFactory`（动态模型选择）、`ToolRegistry`（工具按需加载）、`PromptTemplateLoader`（角色×场景提示词）、`SessionManager`/`ChatMemoryManager`（会话管理）的桥接
*   **串行编排**: 支持 Agent A -> Agent B -> Agent C 的顺序执行，前一个 Agent 的输出通过 `AgenticScope` 自动传递给下一个
*   **并行编排**: 支持多个 Agent 同时执行同一任务，最后汇总结果
*   **条件分支编排**: 支持根据条件走不同分支（如"简单问题单 Agent 回答，复杂问题多 Agent 协作"）
*   **循环编排**: 支持 Agent 循环执行直到满足退出条件（如"评分-修订"循环直到质量达标）
*   **Supervisor 层级编排**: 支持主控 Agent 负责任务拆解和分发，子 Agent 执行具体任务，主控汇总结果
*   **失败处理**: Agent 执行失败时自动重试（默认 3 次），全部失败后工作流暂停在失败步骤，支持断点续执行
*   **状态追踪**: 工作流执行状态在内存中追踪，包括当前步骤、进度、每个 Agent 的执行结果
*   **REST API**: 提供独立的工作流执行 API（模板列表、执行、状态查询、断点续执行）
*   **SSE 执行可视化**: 通过 SSE 推送步骤级进度和每个 Agent 的流式输出
*   **前端管理页面**: 模板列表展示、参数填写、执行可视化（步骤进度 + Agent 流式输出）
*   **预置场景模板**: 提供 5 个开箱即用的工作流模板作为示例和验证用例

### 2.2 阶段拆分计划（Phased Implementation Plan）

> **拆分原则**：每个阶段独立交付、独立验证，前一阶段是后一阶段的前置依赖。每阶段完成后更新 KNOWLEDGE_BASE.md 并进入下一阶段的需求微调。

#### 阶段一：基础适配层 + 串行编排（API 先行）

*   **核心目标**: 验证 `langchain4j-agentic` 集成可行性，交付最小可用的多 Agent 编排能力
*   **范围**:
    - 引入 `langchain4j-agentic:1.17.2-beta27` 依赖，BOM 版本锁定
    - 实现适配层：桥接 `LlmConfigStore`/`ModelFactory`（模型选择）、`ToolRegistry`（工具注入）、`PromptTemplateLoader`（提示词模板）
    - 实现**串行编排**（`sequenceBuilder`）——最稳定、最基础的模式
    - 基础 REST API：模板列表、模板详情、执行工作流、查询执行状态
    - 基础 SSE 事件：`workflow_start`/`step_start`/`token`/`step_complete`/`workflow_complete`/`workflow_failed`
    - 基础失败处理：自动重试（可配置次数）-> 全部失败则工作流终止（**不做断点续执行**）
    - 按 Agent 配置模型（`modelId`）
    - 工具模板预定义
    - 1-2 个串行编排预置模板（如"研究-分析-总结"）
    - **无前端页面**（纯 API 驱动，通过 Swagger/curl 验证）
*   **对应 AC**: AC-001, AC-002, AC-003, AC-008, AC-009, AC-010, AC-011, AC-012, AC-013, AC-014, AC-015, AC-018, AC-019, AC-020, AC-021, AC-022(简化版:终止不可恢复), AC-023, AC-024, AC-025, AC-026, AC-028, AC-030
*   **交付标准**: 编译通过 + 单元测试通过 + 可通过 API 执行串行工作流并收到 SSE 事件

#### 阶段二：多模式编排 + 前端管理页面

*   **核心目标**: 补齐常用编排模式，交付前端可视化操作能力
*   **前置依赖**: 阶段一完成（适配层 + 串行编排 + API 可用）
*   **范围**:
    - 实现**条件分支编排**（`conditionalBuilder`）
    - 实现**循环编排**（`loopBuilder`，含 `maxIterations` 和 `exitCondition`）
    - 实现**并行编排**（`parallelBuilder`）
    - 增强 SSE 事件：新增 `step_retry`/`workflow_paused` 事件
    - 前端编排管理页面：模板列表（卡片布局）、参数填写表单、执行可视化（步骤进度条 + Agent 流式输出折叠面板）
    - 前端导航栏新增"编排"入口
    - 执行历史记录 API + 前端展示
    - 补充条件/循环/并行预置模板（如"智能路由"、"质量评分-修订"、"多角度审查"）
*   **对应 AC**: AC-004, AC-005, AC-006, AC-027, AC-029, AC-032 + 前端交互相关 AC（阶段二补充）
*   **交付标准**: 编译通过 + 前端测试通过 + 可通过前端页面选择模板、填写参数、查看执行过程

#### 阶段三：Supervisor + 断点续执行 + 可视化增强

*   **核心目标**: 交付高级编排能力和容错能力
*   **前置依赖**: 阶段二完成（多模式编排 + 前端可用）
*   **范围**:
    - 实现 **Supervisor 层级编排**（`supervisorBuilder`，含独立主控模型配置）
    - 实现**断点续执行**：自实现内存版 `AgenticScopeStore`，工作流暂停后可从失败步骤恢复
    - 前端失败暂停状态 UI：失败步骤高亮、"恢复执行"和"终止"按钮
    - Supervisor 预置模板（如"任务拆解-执行-汇总"）
    - 执行可视化增强：Supervisor 模式的子任务调度过程展示
*   **对应 AC**: AC-007, AC-016, AC-017, AC-031
*   **交付标准**: 编译通过 + 测试通过 + Supervisor 工作流可执行 + 断点续执行可验证

### 2.3 不在本次范围（Out of Scope）

*   **可视化拖拽编排** - 实现复杂度最高，需要前端画布组件和后端解析引擎，后续迭代考虑
*   **人工审批（HITL）** - `langchain4j-agentic` 的 HITL 跨进程恢复需要 1.18.0-beta28 版本，当前 1.17.2-beta27 不支持 crash-resilient 恢复，后续迭代升级版本后实现
*   **工作流状态持久化到数据库** - 本次仅内存存储（与项目当前存储形态一致），后续接入 MySQL/Milvus 时实现
*   **集成到现有对话页面** - 对话页面保留现有通用功能，不与具体业务场景的 Agent 耦合
*   **用户自定义工作流** - 本次仅支持开发者通过代码预定义的模板，不支持用户在前端创建/修改工作流定义
*   **工作流版本管理** - 模板定义在代码中，无版本管理需求
*   **工作流定时调度** - 不支持定时/周期性执行工作流

## 3. 用户角色 (Actors)

*   **开发者 (Developer)**: 通过 Java 代码定义工作流模板（`@Agent` 接口 + `AgenticServices` 构建器），配置 Agent 的模型、工具和提示词
*   **终端用户 (End User)**: 通过前端编排管理页面选择模板、填写参数、执行工作流并查看执行过程
*   **API 调用方 (API Caller)**: 通过 REST API 程序化调用工作流，获取执行结果

## 5. 详细需求与流程 (Detailed Requirements)

### 5.1 核心流程

#### 5.1.1 工作流模板定义流程（开发者侧）

1. 开发者定义若干 Agent 接口（使用 `@Agent` + `@SystemMessage` + `@UserMessage` 注解）
2. 开发者在 `@Configuration` 类中通过 `AgenticServices` 构建器组合 Agent，形成工作流模板
3. 每个模板声明：名称、描述、所需参数、编排模式（串行/并行/条件/循环/Supervisor）
4. 系统启动时自动扫描并注册所有工作流模板
5. 模板注册后可通过 API 和前端页面使用

#### 5.1.2 工作流执行流程（用户侧）

1. 用户打开前端编排管理页面
2. 系统展示可用的工作流模板列表（名称、描述、编排模式图标、所需参数）
3. 用户选择一个模板，系统展示参数填写表单
4. 用户填写参数，点击"执行"
5. 系统创建工作流执行实例，分配执行 ID
6. 系统按编排模式执行 Agent 序列，通过 SSE 推送事件：
   - `workflow_start`: 工作流开始（含执行 ID、模板名称、参数摘要）
   - `step_start`: 某个 Agent 开始执行（含 Agent 名称、描述）
   - `token`: Agent 的流式输出片段
   - `step_complete`: Agent 执行完成（含输出结果摘要、耗时）
   - `step_error`: Agent 执行失败（含错误信息、重试次数）
   - `step_retry`: Agent 开始重试（含重试次数、剩余重试次数）
   - `workflow_complete`: 工作流完成（含最终结果、总耗时）
   - `workflow_failed`: 工作流失败（含失败步骤、错误信息）
   - `workflow_paused`: 工作流暂停在失败步骤（含可恢复提示）
7. 前端实时展示步骤进度条和每个 Agent 的流式输出
8. 工作流完成后展示最终结果
9. 若 Agent 失败且重试耗尽，工作流暂停，用户可选择"从断点恢复"或"终止"

#### 5.1.3 断点续执行流程

1. 工作流在某个 Agent 失败后暂停，记录当前执行位置（已完成的步骤、失败步骤、AgenticScope 状态）
2. 用户在前端看到"工作流已暂停"提示，可选择"恢复执行"或"终止"
3. 用户点击"恢复执行"，系统从失败的 Agent 重新开始执行
4. 已完成步骤的结果从内存状态中恢复，不重新执行
5. 若恢复后再次失败，重复暂停-恢复流程

#### 5.1.4 并发执行流程

1. 用户（或多个用户）同时发起多个工作流执行
2. 系统为每个执行分配独立的执行 ID 和 AgenticScope
3. 各工作流独立执行，互不干扰
4. 每个工作流的 SSE 事件通过执行 ID 区分

### 5.2 交互/界面规则 (UI/UX Rules)

*   **模板列表页**: 卡片式布局展示模板，每张卡片包含模板名称、描述、编排模式标签（串行/并行/条件/循环/Supervisor）、Agent 数量
*   **参数填写表单**: 根据模板声明的参数动态生成表单，必填参数标注星号，参数含类型提示（文本/数字/选择框）
*   **执行可视化页面**: 上方为步骤进度条（显示当前步骤/总步骤数），下方为 Agent 输出区域（每个 Agent 一个折叠面板，流式输出实时追加）
*   **失败暂停状态**: 页面显示失败步骤高亮红色，提供"恢复执行"和"终止"两个按钮
*   **执行中状态**: 输入框禁用，执行按钮变为"停止"按钮
*   **设计风格**: 与现有前端保持一致的 Refined Dark Tech 暗色科技风

### 5.3 业务规则 (Business Rules)

*   **BR-APP-001**: 工作流模板必须通过 Java 代码定义，在应用启动时自动注册，不支持运行时动态创建
*   **BR-APP-002**: 每个模板必须声明唯一名称和描述，名称不允许重复
*   **BR-APP-003**: 每个模板必须声明所需参数（参数名、类型、是否必填、描述）
*   **BR-APP-004**: 工作流中的每个 Agent 可以配置不同的 LLM 模型（通过 `modelId` 指定），未配置时使用系统默认 chat 模型
*   **BR-APP-005**: Agent 可用工具在模板中预定义，用户执行时不可修改工具集
*   **BR-APP-006**: Agent 执行失败时自动重试，默认重试 3 次，可在模板级别配置
*   **BR-APP-007**: 重试全部失败后工作流暂停在失败步骤，不自动跳过
*   **BR-APP-008**: 工作流执行状态（含 AgenticScope 共享变量）存储在内存中，应用重启后丢失
*   **BR-APP-009**: 断点续执行仅在工作流处于"暂停"状态时可用，已完成或已终止的工作流不可恢复
*   **BR-APP-010**: 工作流执行通过 SSE 推送实时事件，事件格式与现有对话 SSE 事件格式保持一致的协议风格
*   **BR-APP-011**: 现有对话页面（SimpleAgent）的功能不受编排模块影响，两个系统完全独立
*   **BR-APP-012**: Supervisor 模式使用独立的主控模型（建议使用强模型），子 Agent 可使用更快模型以降低成本
*   **BR-APP-013**: 工具在 Agent 构建时绑定，工具变更（如 MCP Server 断线、知识库删除）需重建对应 Agent 实例
*   **BR-APP-014**: 循环工作流必须配置 `maxIterations`（最大迭代次数），防止无限循环
*   **BR-APP-015**: 条件分支工作流的每个分支条件为 `Predicate<AgenticScope>`，运行时评估
*   **BR-APP-016**: 前端编排管理页面作为独立导航入口，与现有"对话"、"知识库"、"设置"页面并列

## 6. 验收标准 (Acceptance Criteria)

> **重要**：以下验收标准是后续技术方案、任务规划和 TDD 测试用例的直接依据。每条 AC 必须使用 Given-When-Then 格式，必须可被测试验证。
>
> **阶段标注**：每条 AC 标注所属实施阶段（[P1]=阶段一, [P2]=阶段二, [P3]=阶段三），阶段划分详见第 2.2 节。

### 6.1 正常流程 (Happy Path)

- [ ] **AC-001** [P1]: 查看工作流模板列表
    - Given: 系统已启动，至少注册了 1 个工作流模板
    - When: 用户通过 GET /api/app/workflows 请求模板列表
    - Then: 返回模板列表，每个模板包含名称、描述、编排模式、Agent 数量、所需参数定义

- [ ] **AC-002** [P1]: 查看模板详情
    - Given: 系统已注册模板"研究-分析-总结"
    - When: 用户通过 GET /api/app/workflows/{templateId} 请求模板详情
    - Then: 返回模板完整信息，包含每个 Agent 的名称、描述、使用的模型配置、工具列表、参数定义（名称/类型/是否必填/描述）

- [ ] **AC-003** [P1]: 执行串行工作流
    - Given: 用户已选择"研究-分析-总结"串行模板并填写了参数（主题："AI Agent 技术趋势"）
    - When: 用户通过 POST /api/app/workflows/{templateId}/execute 提交执行请求
    - Then: 返回执行 ID，工作流按顺序执行"研究 Agent" -> "分析 Agent" -> "总结 Agent"，每个 Agent 的输出自动传递给下一个，最终返回总结结果

- [ ] **AC-004** [P2]: 执行并行工作流
    - Given: 用户已选择"多角度审查"并行模板并填写了参数（待审查内容）
    - When: 用户提交执行请求
    - Then: 多个审查 Agent（如安全审查、性能审查、风格审查）同时执行，各自独立输出结果，最终汇总为综合审查报告

- [ ] **AC-005** [P2]: 执行条件分支工作流
    - Given: 用户已选择"智能路由"条件分支模板并填写了参数（问题内容）
    - When: 用户提交执行请求
    - Then: 系统根据问题复杂度评估条件，自动路由到"简单回答 Agent"或"复杂拆解 Agent"分支，仅执行匹配分支的 Agent

- [ ] **AC-006** [P2]: 执行循环工作流
    - Given: 用户已选择"质量评分-修订"循环模板并填写了参数（初稿内容）
    - When: 用户提交执行请求
    - Then: 系统执行"评分 Agent"评估质量，若分数低于阈值则执行"修订 Agent"改进，循环执行直到分数达标或达到最大迭代次数（如 5 次），返回最终修订结果和评分

- [ ] **AC-007** [P3]: 执行 Supervisor 层级工作流
    - Given: 用户已选择"任务拆解-执行-汇总"Supervisor 模板并填写了参数（复杂任务描述）
    - When: 用户提交执行请求
    - Then: 主控 Agent 接收任务并自主拆解为子任务，依次调度子 Agent 执行各子任务，最终汇总所有子 Agent 的结果生成综合报告

- [ ] **AC-008** [P1]: 实时查看步骤进度
    - Given: 用户已发起一个串行工作流执行（3 个 Agent）
    - When: 工作流正在执行第 2 个 Agent
    - Then: 前端通过 SSE 收到 `step_start` 事件显示"Agent 2/3 正在执行"，步骤进度条显示 2/3，第 1 个 Agent 显示为已完成状态

- [ ] **AC-009** [P1]: 查看 Agent 流式输出
    - Given: 工作流正在执行，某个 Agent 正在生成回复
    - When: Agent 逐字生成输出内容
    - Then: 前端通过 SSE 收到 `token` 事件，实时追加该 Agent 的输出文本到对应的折叠面板中，显示打字机效果

- [ ] **AC-010** [P1]: 查看工作流最终结果
    - Given: 工作流所有 Agent 执行完成
    - When: 最后一个 Agent 完成输出
    - Then: 前端收到 `workflow_complete` 事件，展示最终结果，显示总耗时和各步骤耗时，执行按钮恢复可用状态

- [ ] **AC-011** [P1]: 通过 REST API 调用工作流
    - Given: 系统已注册工作流模板
    - When: API 调用方通过 POST /api/app/workflows/{templateId}/execute 发送请求（含参数和 modelId）
    - Then: 返回执行 ID 和 SSE 流地址，调用方可通过 SSE 流地址订阅执行事件，或通过 GET /api/app/workflows/executions/{executionId} 查询执行状态和结果

- [ ] **AC-012** [P1]: 开发者定义工作流模板
    - Given: 开发者在 Java 代码中定义了 Agent 接口和 `@Configuration` 构建方法
    - When: 应用启动
    - Then: 工作流模板自动注册到模板注册中心，可通过 API 查询到，模板包含声明的名称、描述、参数定义和编排模式

### 6.2 边界与异常 (Edge & Error Cases)

- [ ] **AC-013** [P1]: 请求不存在的模板
    - Given: 系统中不存在 ID 为"non-existent"的模板
    - When: 用户通过 GET /api/app/workflows/non-existent 请求详情
    - Then: 返回 404 错误，错误码 `WORKFLOW_NOT_FOUND`，提示"工作流模板不存在"

- [ ] **AC-014** [P1]: 缺少必填参数
    - Given: 模板"研究-分析-总结"需要参数"topic"（必填）
    - When: 用户提交执行请求时未提供"topic"参数
    - Then: 返回 400 错误，错误码 `WORKFLOW_PARAM_MISSING`，提示"缺少必填参数：topic"

- [ ] **AC-015** [P1]: Agent 执行失败触发自动重试
    - Given: 工作流正在执行，第 2 个 Agent 因 LLM 调用超时失败
    - When: Agent 执行抛出异常
    - Then: 系统自动重试该 Agent（默认最多 3 次），每次重试通过 SSE 推送 `step_retry` 事件显示重试次数，重试成功后继续执行后续步骤

- [ ] **AC-016** [P3]: 重试耗尽后工作流暂停
    - Given: 某个 Agent 连续重试 3 次全部失败
    - When: 最后一次重试失败
    - Then: 工作流状态变为"暂停"（PAUSED），通过 SSE 推送 `workflow_paused` 事件，包含失败步骤名称、错误信息和可恢复提示，前端显示"恢复执行"和"终止"按钮

- [ ] **AC-017** [P3]: 断点续执行
    - Given: 工作流处于"暂停"状态，第 2 个 Agent 失败，第 1 个 Agent 已完成
    - When: 用户点击"恢复执行"
    - Then: 系统从第 2 个 Agent 重新开始执行，第 1 个 Agent 的结果从内存状态恢复不重新执行，通过 SSE 推送恢复后的执行事件

- [ ] **AC-018** [P1]: Agent 模型未配置
    - Given: 模板中某个 Agent 配置了 `modelId` 但该模型在 `LlmConfigStore` 中不存在
    - When: 用户提交执行请求
    - Then: 返回 400 错误，错误码 `WORKFLOW_MODEL_NOT_FOUND`，提示"Agent {agentName} 配置的模型不存在，请先在 LLM 配置页面添加"

- [ ] **AC-019** [P1]: 模板引用的工具未注册
    - Given: 模板中某个 Agent 引用了工具"builtin:httpGet"，但该工具未在 `ToolRegistry` 中注册
    - When: 应用启动时注册模板
    - Then: 启动日志记录 WARNING"模板 {templateName} 的 Agent {agentName} 引用了未注册的工具 builtin:httpGet，该 Agent 将在不包含此工具的情况下构建"，不阻塞应用启动

- [ ] **AC-020** [P1]: 并发执行多个工作流
    - Given: 用户同时发起两个工作流执行请求
    - When: 两个工作流同时执行
    - Then: 两个工作流分配不同的执行 ID，各自独立执行互不干扰，SSE 事件通过执行 ID 区分，两个工作流可同时完成或分别失败

- [ ] **AC-021** [P1]: Agent 输出为空
    - Given: 工作流中某个 Agent 返回空字符串
    - When: 该 Agent 执行完成
    - Then: 系统将空字符串写入 `AgenticScope`，后续 Agent 接收到空输入时正常执行（不抛异常），`step_complete` 事件标注"输出为空"

- [ ] **AC-022** [P1]: 用户中止工作流执行
    - Given: 工作流正在执行中
    - When: 用户点击"停止"按钮（前端发送 DELETE /api/app/workflows/executions/{executionId}）
    - Then: 工作流立即终止，正在执行的 Agent 中断，通过 SSE 推送 `workflow_failed` 事件标注"用户主动终止"，执行状态变为"已终止"（TERMINATED），不可恢复

- [ ] **AC-023** [P1]: 工作流执行超时
    - Given: 工作流配置了全局超时时间（默认 5 分钟）
    - When: 工作流执行时间超过超时阈值
    - Then: 工作流自动终止，通过 SSE 推送 `workflow_failed` 事件标注"执行超时"，执行状态变为"超时"（TIMEOUT），不可恢复

### 6.3 业务规则验证 (Business Rules)

- [ ] **AC-024** [P1]: 模板启动时自动注册
    - Given: 开发者在代码中定义了 3 个工作流模板
    - When: 应用启动完成
    - Then: GET /api/app/workflows 返回 3 个模板，模板信息与代码定义一致

- [ ] **AC-025** [P1]: 工具在模板中预定义不可修改
    - Given: 模板"研究-分析-总结"的"研究 Agent"预定义了工具 [builtin:httpGet, rag:knowledge_base_1]
    - When: 用户通过 API 或前端查看模板详情
    - Then: 返回的 Agent 工具列表与预定义一致，执行 API 不接受工具参数，用户无法修改工具集

- [ ] **AC-026** [P1]: 重试次数可配置
    - Given: 开发者为模板"质量评分-修订"配置了 `maxRetries=5`
    - When: 模板中某个 Agent 执行失败
    - Then: 系统自动重试最多 5 次（而非默认的 3 次），每次重试推送 `step_retry` 事件

- [ ] **AC-027** [P2]: 查看执行历史记录
    - Given: 用户之前执行过 3 个工作流（2 个完成，1 个暂停）
    - When: 用户通过 GET /api/app/workflows/executions 查询执行历史
    - Then: 返回执行列表，每条记录包含执行 ID、模板名称、状态（COMPLETED/PAUSED/TERMINATED/TIMEOUT）、开始时间、结束时间、最终结果摘要

- [ ] **AC-028** [P1]: 按 Agent 配置不同模型
    - Given: 模板中"研究 Agent"配置了 `modelId="vendor1:doubao-seed-2.0-pro"`，"总结 Agent"配置了 `modelId="vendor1:doubao-seed-2.0-lite"`
    - When: 工作流执行
    - Then: "研究 Agent"使用 pro 模型执行，"总结 Agent"使用 lite 模型执行，两个 Agent 的调用日志显示不同的模型名称

- [ ] **AC-029** [P2]: 循环工作流最大迭代限制
    - Given: 循环模板配置了 `maxIterations=5`
    - When: 循环条件始终不满足（如评分始终低于阈值）
    - Then: 循环执行 5 次后自动退出，返回第 5 次的结果，`workflow_complete` 事件标注"达到最大迭代次数退出"

- [ ] **AC-030** [P1]: 现有对话页面不受影响
    - Given: 编排模块已部署且注册了多个工作流模板
    - When: 用户使用现有对话页面进行单 Agent 对话
    - Then: 对话功能完全正常，SimpleAgent 行为不变，对话页面无编排相关 UI 元素

- [ ] **AC-031** [P3]: Supervisor 使用独立主控模型
    - Given: Supervisor 模板配置了 `supervisorModelId="vendor1:doubao-seed-2.0-pro"`，子 Agent 使用 `agentModelId="vendor1:doubao-seed-2.0-lite"`
    - When: Supervisor 工作流执行
    - Then: 主控 Agent 使用 pro 模型进行任务拆解和调度决策，子 Agent 使用 lite 模型执行具体任务

- [ ] **AC-032** [P2]: 前端编排管理页面独立入口
    - Given: 应用已启动，编排模块已加载
    - When: 用户打开前端导航栏
    - Then: 导航栏显示"编排"入口（与"对话"、"知识库"、"设置"并列），点击后进入编排管理页面，展示模板列表

- [ ] **AC-033** [CR-001]: 不同编排模式的差异化执行页面
    - Given: 用户已选择"多角度审查"并行模板（或任意非串行模板），系统已展示该模板的执行页面
    - When: 用户观察执行页面的布局结构
    - Then: 执行页面按该编排模式专属布局展示（并行=多列并排各分组输出；循环=轮次时间线；条件=分岔路径高亮；Supervisor=子任务卡片+调度过程），与串行模板的执行页面布局有显著差异；5 种编排模式各有独立的执行视图组件

- [ ] **AC-034** [CR-001]: 执行历史详情查看
    - Given: 用户之前执行过工作流并已完成，执行历史列表中存在该记录
    - When: 用户在执行历史列表中点击某条记录
    - Then: 展开详情面板，显示完整执行步骤（每步 Agent 名称、状态、耗时、输出内容）和最终结果全文，而非仅 50 字截断摘要
