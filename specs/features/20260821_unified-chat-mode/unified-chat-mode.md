## 1. 背景与价值 (Context & Value)

*   **背景**: agent-demo 前端对话页现有"自动（普通）、深度思考、任务拆解、人机交互"四种模式（由 3 个独立开关组合而来），用户需理解各模式含义并手动切换，认知负担重；且组合行为不直观（任务拆解与人机交互在路由上互斥，同时开启时人机交互失效）。同时，人机交互的选项卡片结构与样式简陋：text 型追问无任何交互控件（纯文本气泡）、confirm 型选项横向换行排列不美观，两种形态交互模式割裂。
*   **目标**: 将四种模式融合为**一个统一默认模式**——以深度思考为基础，系统自动判断是否需要任务拆解与人机交互；用户可通过 `/plan` 指令强制拆解；统一人机交互卡片形态（垂直选项 + 内嵌输入框 + 自由输入兜底）。
*   **关联**: 演进自 `specs/features/20260820_agent-human-interaction/`（HITL）、`specs/features/2026-07-23/复杂任务拆解/`（任务拆解）、`specs/features/20260722_深度思考模式优化-ReAct与工具调用/`（深度思考）。

## 2. Agent 角色定义 (Agent Persona)

### 2.1 身份定位

*   **角色名称**: 统一对话模式（Unified Chat Mode，非独立 Agent，是现有单 Agent 对话能力的模式融合演进）
*   **角色类型**: 混合型（对话 + 任务拆解执行 + 澄清确认）
*   **身份描述**: 一个"自主决策的智能执行者"——以深度思考为基础推理引擎，自主判断任务复杂度并决定拆解或直答，执行中遇到信息缺口或关键操作时主动向用户发起交互
*   **核心价值**: 用户零模式认知成本、零切换成本；复杂任务自动获得拆解编排；关键决策保留用户掌控

### 2.2 目标用户与场景

*   **目标用户**: agent-demo 的学习者、开发者、API 调用方
*   **使用场景**:
    *   日常对话/简单问答：直接深度思考回答
    *   复杂多步任务（调研、分析、报告）：自动拆解为子任务逐步执行
    *   明确要求拆解：`/plan` 前缀强制拆解
    *   任务执行中信息不足（如缺订单号）：卡片内嵌输入框追问
    *   副作用操作前（删除/修改/外发）：垂直选项卡片确认
*   **交互风格**: 简洁直接、过程透明（思考过程与拆解进度可见）、关键节点主动交互

## 3. 能力边界与自主性 (Capability & Autonomy)

### 3.1 能力清单（In Scope）

*   **统一默认模式**: 前端移除深度思考/任务拆解/人机交互三个开关，所有对话走统一流程
*   **前置规划判断**: 每条消息（无 `/plan` 前缀）先执行一次轻量规划调用判断任务复杂度：复杂任务自动进入拆解执行，简单任务直接深度思考回答
*   **强制拆解指令**: `/plan` 前缀命令强制进入任务拆解（跳过动态判断），剥离前缀后的内容作为任务主题
*   **全路径人机交互**: askUser 能力在直答路径与子任务执行路径均可用（子任务执行中可暂停-恢复）
*   **统一交互卡片**: "问题区 + 交互区"的统一卡片结构；text 型展示内嵌输入框，confirm 型展示垂直整行选项列表 + "其他"自由输入兜底
*   **过程可视化**: 深度思考折叠块、任务计划与子任务执行进度、最终总结

### 3.2 能力禁区（Out of Scope）

*   **工作流编排 HITL** - 本期不实现，后续扩展至工作流编排系统
*   **独立提问超时策略** - 复用现有会话超时（30 分钟）自然清理
*   **提示注入防护** - 本期不实现，用户回复视为可信输入（`/plan` 指令仅在用户输入层识别，详见 6.6）
*   **多 Agent 协作 HITL** - 本期不涉及多 Agent 场景的人工介入
*   **同步 /chat 接口的模式升级** - 同步接口维持现状，仅流式接口支持统一模式

### 3.3 自主性级别

*   **级别**: L2 - 确认后执行
*   **说明**: 无副作用的查询/计算/拆解编排由 Agent 自主推进；有副作用的操作与信息不足场景必须暂停等待用户；是否拆解由系统自主判断并对用户透明展示
*   **人类介入点**:
    *   信息澄清：缺少必要参数无法继续时（text 卡片输入框 / confirm 卡片选项）
    *   关键操作确认：即将执行有副作用操作时（confirm 卡片）
    *   追问超限：同一问题追问 3 次无效后终止任务并告知用户

### 3.4 知识边界

*   **知识范围**: 依赖现有 Agent 的知识范围（系统提示词 + 工具能力 + RAG 知识库）
*   **超出边界处理**: 告知用户无法处理的原因，并建议可能的替代方案

## 4. 工具与动作空间 (Tools & Action Space)

### 4.1 工具清单

| 工具名称 | 用途 | 输入 | 输出 | 副作用 | 权限 | 限制 | 常见失败场景 |
|---------|------|------|------|--------|------|------|-------------|
| askUser | 向用户发起提问/确认（参数契约不变） | type（text/confirm）、question（非空）、options（confirm 型必填 2-4 项） | 用户回复文本 | 无 | 只读 | 同一问题最多追问 3 次；同一会话同一时间仅一个待答问题；不消耗 ReAct 迭代次数 | 用户长时间不回复（依赖会话超时清理） |
| 前置规划判断（内部机制，非 @Tool） | 判断消息是否需要任务拆解 | 用户消息 + 对话上下文 | 拆解决策（子任务列表或"不拆解"） | 无 | 只读 | 每条消息最多一次；失败即降级直答 | 调用超时/异常/返回解析失败（降级为直接回答） |
| /plan 指令解析（用户输入层约定，非 @Tool） | 用户强制指定任务拆解 | 消息前缀 `/plan` | 强制拆解标记 + 剥离前缀后的任务内容 | 无 | 只读 | 仅识别用户消息的前缀；剥离后无有效内容则提示补充 | 消息仅含 `/plan` 无任务内容 |

> 其余现有工具（计算器/时间/HTTP/文件/MCP/RAG）契约不变。前端渲染形态升级（统一交互卡片）**不改变** askUser 工具的参数契约。

### 4.2 工具间关系

*   **依赖关系**: askUser 的输出（用户回复）作为 Agent 后续推理的上下文输入；子任务执行中 askUser 暂停整个拆解流程，恢复后继续执行剩余子任务
*   **互斥关系**: askUser 与其他工具不在同一 ReAct 步骤中同时调用（askUser 触发暂停）；前置规划判断与 askUser 不会同时发生（判断先于执行）
*   **编排策略**: 前置规划判断先行（或 `/plan` 跳过判断），决定"拆解执行（Plan-Execute）"或"直接回答（ReAct）"路径；两条路径中 askUser 均可触发暂停-恢复

### 4.3 工具选择策略

*   Agent 通过 ReAct 推理自主判断是否调用 askUser（即"动态判断是否需要人机交互"）
*   开放式追问（缺少参数，需用户填写信息）用 type=text；确认型交互（副作用操作确认、方案选择）用 type=confirm 并提供 2-4 个选项
*   无副作用的查询/计算操作无需确认，Agent 直接执行

## 5. 推理流程与记忆策略 (Reasoning & Memory)

### 5.1 推理模式

*   **主要模式**: 混合（前置路由判断 + ReAct / Plan-Execute）
*   **模式选择策略**:

```
用户消息
 ├─ /plan 前缀 -> 剥离前缀，强制拆解（跳过判断）
 └─ 普通消息 -> 前置规划判断（轻量同步调用）
     ├─ 判定复杂 -> 拆解执行：计划 -> 逐子任务 ReAct（思考流 + askUser 拦截）-> 总结
     └─ 判定简单 -> 直接深度思考 ReAct 回答（思考流 + askUser 拦截）
```

*   **判断结果透出**: 判定拆解时通过任务计划与子任务进度事件展示（复用现有 task_* 事件体系）；判定直答时不展示判断过程，直接进入流式回答
*   **最大执行步骤**: 每个子任务的 ReAct 循环受现有 `agent.max-iterations=10` 约束；子任务数量上限沿用现有配置（taskBreakdownMaxSubtasks）
*   **非功能性约束**: 前置规划判断为单次轻量同步调用；判定简单的消息应尽快进入流式回答（判断调用的模型选择/超时预算在技术方案阶段确定）

### 5.2 澄清策略

*   **主动澄清条件**: 用户指令缺少必要参数、存在歧义、面临多种可选方案、即将执行副作用操作——**直答路径与子任务执行路径均适用**
*   **自主推进条件**: 无副作用的查询/计算操作、指令明确且参数完整、Agent 有足够信息自主决策
*   **最大澄清轮次**: 同一问题最多追问 3 次，超限终止任务并告知用户

### 5.3 短期记忆（对话内）

*   **上下文保留轮次**: 复用现有短期记忆窗口（20 条消息），跨"拆解-追问-恢复"周期保持完整上下文
*   **上下文溢出处理**: 复用现有 FIFO 淘汰策略

### 5.4 长期记忆（跨会话）

*   **是否需要**: 否（与现状一致）
*   **记忆内容**: 不适用
*   **遗忘策略**: 不适用

## 6. 护栏安全与降级策略 (Guardrails & Fallback)

### 6.1 内容安全规则

*   **必须拒绝的请求**: 继承现有 Agent 的内容安全规则
*   **标准拒绝话术**: 继承现有拒绝话术
*   **敏感话题处理**: 继承现有处理策略

### 6.2 幻觉防护

*   **回答依据**: 继承现有策略（自身知识 + 工具/知识库数据）
*   **无结果处理**: 如实告知无法获取相关信息，不编造内容

### 6.3 敏感信息处理

*   **输入侧**: 用户回复视为可信输入，与现有对话流安全级别一致
*   **输出侧**: Agent 提问内容不应包含不必要的敏感信息

### 6.4 工具失败降级

| 工具/机制 | 失败场景 | 降级策略 | 是否转人工 |
|------|---------|---------|-----------|
| 前置规划判断 | 调用超时/异常/结果解析失败 | 降级为直接深度思考回答，不中断对话 | 否 |
| /plan 指令 | 剥离前缀后无有效任务内容 | 提示用户提供任务描述，不进入拆解 | 否 |
| askUser | 用户长时间不回复 | 依赖会话超时（30 分钟）自然清理，下次消息新建会话 | 否 |
| askUser | 回复持续模糊/无效 | 最多追问 3 次（每次提供选项引导），超限终止任务并告知 | 否 |
| askUser | 用户取消（发送"取消"或点选取消选项） | 停止当前任务，确认取消，准备接收新指令 | 否 |
| 子任务执行 | 某子任务执行失败 | 沿用现有策略：失败即停，剩余子任务标记取消 | 否 |

### 6.5 人机协作机制

*   **升级条件**: 经用户澄清后仍无法完成任务（工具失败、能力超出边界）
*   **升级方式**: Agent 直接告知用户无法继续的原因与建议的后续步骤（无人工转接机制，本项目为学习示例）
*   **交接信息**: 当前任务状态、已尝试的方案、失败原因

### 6.6 提示注入防护

*   **攻击识别**: 本期不实现通用注入检测，与现有对话流安全级别一致
*   **处理策略**: 用户回复视为可信输入
*   **/plan 指令边界**: `/plan` 仅在**用户消息前缀**层面识别并剥离，不进入推理上下文；工具返回内容、知识库检索内容中出现的 "/plan" 字样**不触发**强制拆解
*   **工具返回防护**: 不适用（askUser 返回的是用户回复）

### 6.7 权限与身份校验

*   **身份确认机制**: 继承项目现有策略（无认证机制，学习示例工程）
*   **防越权策略**: 继承现有策略（会话按 sessionId 隔离）
*   **数据隔离**: pending 交互状态按 sessionId 隔离，不同会话互不影响

## 7. 验收标准 (Acceptance Criteria)

> **重要**：以下验收标准是后续 Prompt 工程、工具开发和评估测试的直接依据。每条 AC 使用 Given-When-Then 格式，Given 描述上下文/状态，When 描述触发条件，Then 描述预期行为。AI Agent 的 AC 关注**行为约束**而非精确输出。

### 7.1 正常交互流程 (Normal Interaction)

- [ ] **AC-N01**: 统一默认模式
    - Given: 任意会话，前端已无任何模式开关（深度思考/任务拆解/人机交互开关均已移除）
    - When: 用户发送普通消息（无 /plan 前缀）
    - Then: 系统应以深度思考为基础处理消息并展示思考折叠块（流式中展开、完成后折叠）；不应出现任何模式选择/开关 UI；不应要求用户指定处理模式

- [ ] **AC-N02**: 复杂任务自动拆解
    - Given: 默认模式，用户发送复杂多步任务消息（如"调研X并输出报告"），无 /plan 前缀
    - When: 前置规划判定该任务需要拆解
    - Then: Agent 应自动进入拆解执行并展示任务计划与逐任务执行进度；不应要求用户手动开启拆解开关；不应因用户未选择模式而降低处理能力

- [ ] **AC-N03**: 简单任务直接回答
    - Given: 默认模式，用户发送简单消息（如"你好"、"现在几点"）
    - When: 前置规划判定无需拆解
    - Then: Agent 应直接以深度思考模式流式回答；不应展示任务拆解 UI；不应对该消息执行子任务拆解

- [ ] **AC-N04**: /plan 强制拆解
    - Given: 默认模式，用户发送以 /plan 开头的消息（如"/plan 帮我调研竞品并写报告"）
    - When: 系统识别到 /plan 前缀
    - Then: 应剥离前缀后强制进入任务拆解（跳过动态判断），前缀后的内容作为任务主题；不应再执行前置规划判断调用；不应要求用户通过开关触发

- [ ] **AC-N05**: 拆解过程可视化
    - Given: Agent 已自动或强制进入拆解执行
    - When: 拆解各阶段推进（计划生成/子任务执行/总结）
    - Then: 前端应展示子任务列表、每个子任务的执行状态与产出、最终总结；子任务执行中应同步展示思考过程；不应让用户长时间无进度反馈

### 7.2 工具选择与调用 (Tool Selection & Invocation)

- [ ] **AC-T01**: 前置规划判断
    - Given: 默认模式收到一条无 /plan 前缀的消息
    - When: 消息进入处理流程
    - Then: 系统应先执行一次轻量规划判断并按结果路由（拆解/直答）；判断调用失败或结果解析失败时应降级为直接深度思考回答；不应因判断失败中断对话或报错终止

- [ ] **AC-T02**: 开放式追问使用卡片内嵌输入框
    - Given: Agent 执行中（直答路径或子任务路径）缺少必要信息（如订单号）
    - When: Agent 调用 askUser 工具，type=text
    - Then: 前端应展示统一交互卡片（问题文本 + 内嵌输入框 + 提交按钮），用户在卡片内填写并提交后 Agent 从暂停点恢复执行；不应再以无控件的纯文本气泡展示追问；不应强制用户到底部主输入框回复

- [ ] **AC-T03**: 确认型交互使用垂直选项卡片
    - Given: Agent 即将执行有副作用的操作（如删除文件、修改数据、发送请求）
    - When: Agent 调用 askUser 工具，type=confirm，携带 2-4 个选项
    - Then: 前端应展示统一交互卡片（问题文本 + 垂直整行选项列表：每个选项独占一行全宽、含序号与选项文字、hover 高亮、选中后锁定）；用户点击选项后 Agent 恢复执行；选项不应横向流式换行排列

- [ ] **AC-T04**: 选项自由输入兜底
    - Given: confirm 型卡片已展示选项列表
    - When: 所有给定选项均不符合用户意图
    - Then: 卡片应提供"其他"入口，点击后展开输入框允许自由填写；自由填写的回复应与点选选项等效地回传 Agent 并恢复执行；不应限制用户只能从给定选项中选择

- [ ] **AC-T05**: 子任务执行中触发人机交互
    - Given: 拆解执行中，第 N 个子任务缺少必要信息或需确认副作用操作（前序子任务已完成）
    - When: 该子任务的 ReAct 执行调用 askUser 工具
    - Then: Agent 应暂停整个拆解流程并展示交互卡片等待用户回复；用户回复后应从该子任务暂停点继续执行剩余子任务；已完成子任务的结果不应丢失或重跑；不应因暂停导致拆解上下文断裂

### 7.3 安全与护栏 (Safety & Guardrails)

- [ ] **AC-S01**: 副作用操作强制确认
    - Given: Agent 即将执行有副作用的操作（删除/修改/外发请求）
    - When: 用户尚未通过 confirm 卡片确认
    - Then: Agent 不得执行该操作，必须先发起确认并等待用户选择，确认后才执行；/plan 强制拆解不应豁免此规则（拆解出的子任务中含副作用操作时同样必须确认）

- [ ] **AC-S02**: 追问次数上限
    - Given: Agent 已对同一问题追问 3 次，用户每次回复仍模糊或无效
    - When: 达到第 3 次追问上限
    - Then: Agent 应终止当前任务并明确告知用户原因；不应继续追问同一问题；应准备好接收新的用户指令

### 7.4 边界与降级 (Edge Cases & Fallback)

- [ ] **AC-E01**: 规划判断失败降级
    - Given: 前置规划判断调用超时/异常，或返回结果无法解析
    - When: 无法获得有效判断结果
    - Then: 应降级为直接深度思考回答；不应中断对话；不应向用户暴露技术错误细节

- [ ] **AC-E02**: /plan 空内容
    - Given: 用户消息仅含 /plan 或 /plan + 空白字符（无任务描述）
    - When: 剥离前缀后无有效内容
    - Then: 应提示用户提供任务描述；不应以空任务进入拆解；不应报错

- [ ] **AC-E03**: 会话超时清理等待状态
    - Given: Agent 处于"等待用户输入"暂停状态（含子任务执行中暂停）
    - When: 30 分钟内用户未回复，会话超时清理任务执行
    - Then: 等待状态应随会话一起清理；用户下次发送消息时创建新会话；不应残留过期的等待状态

- [ ] **AC-E04**: 等待期间切换话题
    - Given: Agent 正在等待用户对澄清问题的回复
    - When: 用户发送了一条与当前问题完全无关的消息
    - Then: Agent 应识别话题切换并询问用户是否放弃当前任务；不应忽略用户的新消息，也不应在新话题上丢失之前的任务上下文

### 7.5 记忆与上下文 (Memory & Context)

- [ ] **AC-M01**: 跨暂停-恢复的上下文保持
    - Given: Agent 在任务执行中途暂停提问，对话历史中包含之前的交互记录
    - When: 用户回复后 Agent 恢复执行
    - Then: Agent 应能访问完整对话历史（含提问与回复）并整合到后续推理；不应因暂停-恢复丢失任何上下文

- [ ] **AC-M02**: 拆解-追问-恢复链路的上下文连续性
    - Given: 拆解执行中第 2 个子任务触发追问并暂停（子任务 1 已完成）
    - When: 用户回复后恢复执行
    - Then: Agent 应保留子任务 1 的结果、追问上下文与拆解计划，从子任务 2 暂停点继续；不应重跑子任务 1；不应丢失已澄清的信息

### 7.6 人机协作 (Human-in-the-Loop)

- [ ] **AC-H01**: 任务无法完成时的告知
    - Given: Agent 即使经过用户澄清仍无法完成任务（工具失败、能力超出边界）
    - When: Agent 判定无法继续执行
    - Then: 应明确告知用户无法继续的具体原因并建议后续步骤；不应静默放弃或无限重试

- [ ] **AC-H02**: 用户主动取消等待中的交互
    - Given: Agent 正在等待用户回复（统一交互卡片待答状态）
    - When: 用户明确表示取消（发送"取消"文本或点选取消选项）
    - Then: Agent 应停止当前任务并确认取消；应准备好接收新指令；不应继续执行已暂停的任务

## 8. 范围界定 (Scope)

### 8.1 本次范围（In Scope）

*   **前端模式融合**: 移除 MessageInput 三个模式开关（深度思考/任务拆解/人机交互），仅保留统一默认模式；输入框支持 /plan 指令（含可发现性提示）
*   **后端统一路由**: 默认模式 = 前置规划判断 -> 拆解执行或直接回答；全路径启用深度思考与 askUser（含子任务级暂停-恢复）
*   **/plan 强制拆解指令**: 前缀识别、剥离、空内容提示（前端与 API 通用）
*   **子任务级 HITL**: 拆解执行中子任务可触发 askUser 暂停，回复后从暂停点继续剩余子任务
*   **统一交互卡片重构**: 问题区 + 交互区统一结构；confirm 型垂直整行选项（序号 + 文字 + hover 高亮 + 选中锁定）；text 型内嵌输入框 + 提交按钮；confirm 型"其他"自由输入兜底
*   **API 参数清理**: ChatRequest 废弃 enableThinking/enableTaskBreakdown/enableHitl 旧参数，调用方统一走默认模式（强制拆解经 /plan 前缀表达）

### 8.2 不在本次范围（Out of Scope）

*   **工作流编排 HITL** - 下一期扩展（将 askUser 机制集成到工作流 PAUSED 状态）
*   **独立提问超时策略** - 复用会话超时（30 分钟）自然清理
*   **提示注入防护** - 本期信任用户回复，后续可增加检测
*   **多 Agent 协作 HITL** - 不涉及
*   **长期记忆** - 不涉及
*   **同步 /chat 接口的模式升级** - 同步接口维持现状
*   **规划判断的模型路由优化**（如使用独立轻量模型、超时预算）- 技术方案阶段评估
*   **结构化强制拆解 API 字段**（如 forcePlan 布尔字段）- 本期以 /plan 前缀为唯一强制拆解入口，是否补充结构化字段由技术方案阶段评估

### 8.3 评估方式

*   **评估数据来源**: 手动测试场景（前端交互验证）+ 单元测试（后端路由/状态管理/工具调用逻辑）
*   **自动/人工评估**:
    *   前端交互（统一卡片展示、垂直选项、内嵌输入框、兜底输入、拆解可视化）: 人工评估
    *   后端路由逻辑（/plan 解析、规划判断降级、统一模式分流）: 自动化单元测试
    *   子任务 HITL 状态流转（暂停-恢复-上下文保留）: 自动化单元测试
    *   askUser 调用逻辑（参数契约、追问计数）: 自动化单元测试
*   **通过标准**: 所有 AC 通过手动验证或自动化测试覆盖
