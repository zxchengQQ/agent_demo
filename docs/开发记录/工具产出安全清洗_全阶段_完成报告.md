## 1. 业务背景与目标

本次优化**针对具体工具**（HttpTool / FileReadTool / McpToolExecutor / KnowledgeRetrieverTool），
**工具模块架构零变更**（ToolRegistry / ToolExecutor / 权限体系均不改动）。

要解决 3 个问题、落地 4 个优化：

| 问题 | 优化 |
| :--- | :--- |
| 工具返回信息含非法指令，可影响大模型判断 | ① 工具产出数据清洗（分级处置可疑指令） |
| 工具返回文本量过大可能撑爆模型上下文 | ② 字数限制 + 超长存临时文件并告知查询位置 |
| HTML 页面含非法脚本可致脚本注入 | ③ 结果进入上下文前 prompt 优化（外部数据非指令声明） |
| — | ④ 调研现有 agent 开源框架清洗方案（已产出独立调研报告） |

## 6. 关键设计决策

1. **分级处置**（一般标记保留 vs 高危移除占位）——兼顾信息可用性与安全性，避免误杀正常讨论注入话题的文档
2. **递归截断防护**——临时文件回读豁免二次清洗 + 硬截断不落盘，终结"临时文件的临时文件"链条
3. **双构造模式**（无参=disabled 直通 / 带参=真实清洗）——兼容既有测试精确断言，回退开关语义一致
4. **双模块零依赖新增**——清洗器放 tools 模块新包，mcp/rag 已依赖 tools，架构零变更约束满足
5. **temp-dir 约束**——必须位于 `agent.file-allowed-dir`（./data）内，否则模型无法回读临时文件
6. **多构造器注入契约**——工具类同时保留无参构造（测试直通）与带参构造（真实清洗）时，
   必须给带参构造加 `@Autowired` 明确注入目标（HttpTool / FileReadTool / McpToolExecutor /
   KnowledgeRetrieverTool 已统一处理）。否则 Spring 在多构造器且无 `@Autowired` 时会：
   ① 无无参构造（McpToolExecutor / KnowledgeRetrieverTool）→ 启动失败；
   ② 有无参构造（HttpTool / FileReadTool）→ 走无参构造导致生产清洗直通不生效。
   另为 HttpTool 注册 `RestTemplate` Bean（新增 `ToolsConfig`），FileReadTool 目录参数经
   `@Value("${agent.file-allowed-dir:./data}")` 注入（并修正 ToolOutputTempStore 的同名键）
