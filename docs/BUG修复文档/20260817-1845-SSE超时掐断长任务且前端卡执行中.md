# BUG 修复报告

## 基本信息
- 日期：2026-08-17 18:45
- 报告人：AI Assistant
- 模块/功能：agent-demo-web（WorkflowController/AgentController SSE 端点）+ agent-demo-frontend（workflow.ts 断流兜底）
- 严重级别（低/中/高）：高
- 影响范围：所有超过 5 分钟的工作流执行（P1/P2/P3 全部模板）与超过 5 分钟的流式对话；执行被强制终止且前端永久卡"执行中"
 - 严重级别依据：长任务 100% 阻断（5 分钟必现）；前端卡死后无法恢复（执行被标 TERMINATED，非 PAUSED 不可 resume）

## 问题描述
- 期望结果：长时间运行的工作流持续推送 SSE 事件至执行完成（或失败/暂停），前端实时展示并可操作
- 实际结果：执行约 5 分钟后后端日志刷 `WARN WorkflowEventPublisher - SSE 发送失败: event=token, reason=ResponseBodyEmitter has already completed`，流程中断；前端页面永久停留在"执行中"状态，无错误提示，无法继续执行

## 复现步骤（必须可复现）
1) 启动应用，进入"编排"页面选择任一模板（如"任务拆解-执行-汇总"）
2) 输入一个耗时较长的任务（多 Agent/多子任务，端到端超过 5 分钟）
3) 保持页面打开等待约 5 分钟
4) 观察：后端日志出现 `SSE 发送失败: ... ResponseBodyEmitter has already completed`；页面停止更新且一直显示执行中；执行历史中该记录状态为 TERMINATED

## 复现环境
- 设备/系统：Windows / JDK 17 / Spring Boot 3.2.5（内嵌 Tomcat）
- 应用版本/配置：main 分支；`server.tomcat.connection-timeout: 300000`（注意：该配置是 TCP 连接超时，与 SSE 异步超时无关）
- 相关日志：`2026-08-17 18:21:56 [ForkJoinPool.commonPool-worker-2] WARN c.a.a.e.WorkflowEventPublisher - SSE 发送失败: event=token, reason=ResponseBodyEmitter has already completed`

## 定位过程
- 关键线索：`ResponseBodyEmitter has already completed` = emitter 已被 Spring 框架关闭，但工作流线程仍在发送事件
- 排查路径：
  1. 全局检索 `new SseEmitter`：三处端点（WorkflowController.execute L190、WorkflowController.resume L274、AgentController.chatStream L162）均硬编码 `new SseEmitter(300_000L)` = 5 分钟异步超时
  2. 确认触发链：工作流执行 > 300s → Tomcat async timeout → Spring 调用 `emitter.onTimeout`（该回调在 WorkflowExecutionService 中注册为 `cancel(executionId)`）并完成 emitter（响应以 503 结束）
  3. 确认流程中断链：cancelFlag=true → 策略在下一步骤边界抛 WorkflowCancelledException → handleTerminated → 执行标记 **TERMINATED**（终态，不可 resume，这正是"无法继续执行"的原因）→ 向已完成的 emitter 发 workflow_failed → WARN
  4. 确认前端卡死链：emitter 完成后 fetch 的 reader 收到 `done=true` 正常退出解析循环（**不抛异常**）→ `parseSseStream` 无兜底 → 前端永远收不到终态事件（workflow_complete/failed/paused）→ `isRunning` 停留 true
- 根因说明：**双端缺陷叠加**。后端——emitter 固定 5 分钟超时与"工作流可长时间执行"的领域需求冲突（SseEmitter 构造参数单位为毫秒，300_000L 即 5 分钟；原注释误以为与执行超时/Tomcat connection-timeout"对齐"，实际三者互不相干）；前端——只处理了"流读取出错"（catch 分支），未处理"流正常结束但没收到终态事件"的异常断流场景

## 修复方案
- 后端（根因修复）：三处 `new SseEmitter(300_000L)` → `new SseEmitter(0L)`（Servlet 规范：0/负值 = 永不超时）。长任务不再被异步超时掐断；客户端真实断开仍由 `emitter.onError → cancel` 兜底（原语义保留）
- 前端（防御兜底）：`parseSseStream` 跟踪终态事件（workflow_complete/workflow_failed/workflow_paused，新增 `TERMINAL_EVENTS` 集合，`handleWorkflowEvent` 返回是否终态）；流结束（done）但未收到终态事件且非主动 abort → `onError('连接已中断，执行结果未知，请在历史记录中查看执行状态')` → 视图重置 isRunning，页面不再卡死
- 影响评估：正常 <5 分钟的执行行为完全不变；>5 分钟的执行由"必中断+卡死"修复为"持续推送至完成"；任何未来的异常断流（网络闪断、后端重启）前端都会给出明确提示
- 风险点：emitter 永不超时后，若客户端异常消失且 TCP 未断开，连接会保持到执行结束（有界，由工作流时长决定）；demo 场景可接受
- 回滚方案：三处 `new SseEmitter(0L)` 还原为 `300_000L`；前端删除 sawTerminal 跟踪与兜底分支（git revert 即可）

## 遗留问题/后续行动
- `application.yml` 中 `server.tomcat.connection-timeout: 300000` 的注释"SSE 流式接口超时 5 分钟"具有误导性（实为 TCP 连接超时），建议后续修正注释避免再次误判
- 若未来引入反向代理（nginx 等），需同步调大其 proxy_read_timeout，否则会在代理层重现同类掐断
- 客户端断开检测依赖 TCP 层（onError），极端网络下（对端静默消失）连接可能悬挂至执行结束；生产化可考虑心跳事件机制
