# BUG 修复报告

## 基本信息
- 日期：2026-09-02
- 报告人：AI Agent 代码审查员（bugfix-workflow）
- 模块/功能：单 Agent 对话 HITL（人机交互）多轮流程——`tool_confirm` 工具权限确认暂停/恢复 + ReAct 循环 finishReason 处理
- 严重级别（低/中/高）：高
- 影响范围：
  - 所有使用流式对话且触发 ask 级工具确认（tool_confirm）的场景；多轮人机交互（askUser 追问/工具确认混合）场景必现累积劣化
  - 前端对话页（ChatWindow/SSE 流式状态）、后端 AgentController SSE 生命周期、浏览器连接资源
 - 严重级别依据（是否阻断/可绕过/影响用户数）：
  - 阻断级：多轮交互后对话完全不可用（一直"生成中"），页面刷新后应用无法加载（转圈），需等待或重启才能恢复；不可绕过（每次 tool_confirm 均泄漏一条浏览器连接，达到同域连接上限后全部请求挂起）

## 问题描述
- 期望结果：用户发送"帮我查询一下今天的新闻"，经多轮人机交互（Agent askUser 追问 → 用户回答 → ask 级工具 tool_confirm → 用户批准 → 继续）后，Agent 正常生成最终回答，页面恢复可输入状态，可继续对话或刷新页面。
- 实际结果：经过多轮人机交互后流程卡死，前端一直处于"生成中"状态；后端日志无后续输出（恢复请求未到达或无事件产生）；页面直接卡死，刷新页面一直转圈（挂载期 API 请求全部挂起）。

## 复现步骤（必须可复现）
1) 启动后端（8080）与前端（5173），进入对话页，发送"帮我查询一下今天的新闻"
2) Agent 调用 askUser 追问 → 回答追问；Agent 请求 ask 级工具（如 builtin:http 抓取新闻）→ 弹出权限确认卡片 → 点击"批准"
3) 重复第 2 步的多轮确认/追问（约 5~6 轮触发过 tool_confirm 的交互）
4) 观察：页面停留在"生成中"，后端无新日志；此时刷新页面，页面一直转圈（挂载 API 无响应）

## 复现环境
- 设备/系统：WSL2 (Linux) + Windows 浏览器，开发环境
- 应用版本/配置：agent-demo v1.0.0（commit 2ce969f 之后工作区）；后端 8080 / 前端 Vite 5173（/api 代理）；默认工具集（builtin:http 为 ask 级权限）
- 相关依赖或外部条件：浏览器对同域 HTTP/1.1 并发连接上限 6（Vite 代理为 HTTP/1.1）；LLM 厂商为火山引擎方舟（OpenAI 兼容流式）

## 定位过程
- 关键线索：
  1. "后端日志也没有后续的输出"说明恢复请求的异步任务要么未执行、要么无事件产生；
  2. "刷新页面一直转圈"指向浏览器→后端链路资源耗尽（页面挂载 API 全部排队），而非后端死锁；
  3. 复现测试实测：`tool_confirm` 暂停轮的 SseEmitter 永不 complete、无 done 事件（与 `ask_user` 的 done+complete 契约不一致）；
  4. 复现测试另实测：当模型流 finishReason 异常（null/length/content_filter）时，ReAct 循环不退出、不报错，静默空转消耗全部 maxIterations 轮（测试中 10 次 model.stream 调用、无任何 SSE 事件）。
- 排查路径：
  1. 读取 KNOWLEDGE_BASE.md / PROJECT_HABITS.md 建立项目认知；
  2. 沿链路静态分析：AgentController.chatStream → runTracedAsync（commonPool）→ UnifiedChatStream（恢复路由 resumeToolConfirm/resumeDirectAnswer）→ HITLReActStream（ReAct 循环/handleAskUser/handleToolConfirm）→ HumanInteractionManager（pending 状态机）→ 前端 ChatWindow.sendMessage/streamChat（isStreaming 状态机）；
  3. 排除项：HttpTool 有 5s/30s 超时、LLM 流式客户端有 60s 读超时、记忆压缩同步降级 FIFO、sendEvent 全量吞异常、resume 链路状态机正确；
  4. 编写端到端多轮复现测试（真实 Controller/UnifiedChatStream/HITLReActStream/HumanInteractionManager + 桩模型脚本化 4 轮交互），逐轮断言 SSE 事件、emitter 生命周期与 pending 状态；
  5. 修正测试基建竞态（earlySendAttempts 兜底）后，后端 4 轮状态机全部通过——确认后端业务逻辑无卡死，缺陷位于 SSE 流生命周期契约与异常 finishReason 处理。
- 根因说明：
  1. **主因（SSE 连接泄漏）**：`tool_confirm` 事件后后端不发送 done 也不 complete emitter（设计为"挂起等待恢复"）。前端 `streamChat` 以"流关闭"为结束条件，`await streamChat(...)` 永久 pending，该轮 `finally { isStreaming=false }` 永不执行，且浏览器侧该条 SSE 连接永不释放。用户决策后恢复走的是**新** /chat/stream（旧流无人关闭）。多轮交互中每发生一次 tool_confirm 就泄漏一条连接；HTTP/1.1 同域上限 6 条，泄漏积满后：恢复请求在浏览器排队（后端无日志、页面"一直生成中"）、刷新页面时挂载 API 全部排队（转圈）。
  2. **次因（异常 finishReason 静默空转）**：`HITLReActStream.runReActLoop` 仅处理 stop/tool_calls 两种 finishReason；其他值（length/content_filter）或流中断导致 onComplete 未回调（finishReason=null）时，循环既不终止也不报错，静默进行下一迭代，直至耗尽 maxIterations 轮**真实 LLM 调用**，期间无任何 SSE 事件——用户侧表现为"一直生成中"、后端日志无进展。

## 修复方案
- 修改点说明：
  1. `AgentController.registerUnifiedCallbacks` 的 `onToolConfirm`：事件后发送 `done` 并 `emitter.complete()`，与 `ask_user` 同构终止 SSE 流；恢复不依赖旧连接（用户决策后前端发起新 /chat/stream，后端按 hasPending 路由，恢复语义不变）。
  2. `HITLReActStream.runReActLoop`：新增 else 分支处理异常 finishReason——`length` 视为有效截断交付已有内容并正常完成；其余（含 null）立即 WARN + errorConsumer 终止循环，杜绝静默空转。
  3. 前端注释同步（chat.ts / ChatWindow.vue / types/index.ts），后端注释同步（UnifiedChatStream）。
- 影响评估：
  - tool_confirm 契约变更与 ask_user 完全同构，前端 onToolConfirm 仅消费事件载荷渲染卡片（不依赖流保持打开），isWaitingForUserInput 对 permission 卡片本就返回 false，恢复路径零改动；
  - workflow 模块的 tool_confirm 走 WorkflowController 独立 emitter 管理，不受影响；
  - 异常 finishReason 分支仅在原"静默空转"的路径上生效，正常 stop/tool_calls 路径零变更。
- 风险点：
  - 若有第三方调用方依赖"tool_confirm 后流保持打开"（除本仓库前端外），需改为按事件驱动；
  - length 截断语义下用户会看到不完整但可用的回答（原行为是 8 轮无效重试后仍交付，新行为立即交付）。
- 回滚方案：revert 本次两个主改动点（AgentController onToolConfirm 回调块、HITLReActStream else 分支）即可恢复原行为；测试随 revert 一同回滚。
