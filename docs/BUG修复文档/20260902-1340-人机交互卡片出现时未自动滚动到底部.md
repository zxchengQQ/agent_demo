# BUG 修复报告

## 基本信息
- 日期：2026-09-02
- 报告人：AI Agent 代码审查员（bugfix-workflow）
- 模块/功能：前端对话页 HITL 人机交互卡片可见性（MessageList 自动滚动）
- 严重级别（低/中/高）：中
- 影响范围：所有触发人机交互（ask_user 追问 / tool_confirm 工具权限审核）的对话场景；长对话（内容超出一屏）下必现
 - 严重级别依据（是否阻断/可绕过/影响用户数）：
  - 不阻断（可绕过）：用户手动拖动滚动条到底部仍可完成回复/审核；但长对话中卡片出现在视口外，用户不知道 Agent 在等待输入，造成流程"看起来卡住"的等待，影响所有使用 HITL 的用户

## 问题描述
- 期望结果：触发人机交互（ask_user 追问 / tool_confirm 审核）时，页面自动将滚动条定位到末尾，用户实时感知到需要回复/审核并直接操作卡片。
- 实际结果：滚动条停在原位置（流式输出期间用户向上滚动阅读后，卡片渲染在视口外），用户需要手动拖动滚动条到末尾才能发现需要审核。

## 复现步骤（必须可复现）
1) 启动前后端，进入对话页，发送一条会触发多轮人机交互的任务（如"帮我查询一下今天的新闻"）
2) 在 Agent 流式输出期间，用鼠标滚轮向上滚动阅读历史内容（滚动条离开底部）
3) Agent 触发 ask_user 追问或 tool_confirm 审核——观察：页面不自动滚动，卡片在视口外，用户无法实时感知需要审核
4) 手动拖动滚动条到末尾后才能看到卡片

## 复现环境
- 设备/系统：WSL2 + Windows 浏览器，开发环境
- 应用版本/配置：agent-demo v1.0.0 前端（Vue 3 + Vite 5）；对话内容超出一屏出现滚动条
- 相关依赖或外部条件：无外部依赖；纯前端交互行为

## 定位过程
- 关键线索：`MessageList.vue` 现有两个自动滚动 watch 仅监听「消息数量」与「content:status 拼接串」；
- 排查路径：
  1. 定位自动滚动实现（MessageList.vue scrollToBottom，AC-020）；
  2. 梳理 HITL 事件写入路径：`ask_user` → `store.setAskUserData`、`tool_confirm` → `store.setToolConfirmData`——二者只写 `message.askUserData`（及 `askUserHistory`），**不修改 content/status**；
  3. 结论：HITL 触发瞬间两个 watch 均不命中 → 不滚动。（tool_confirm 在前次 BUG 修复后补发了 done → markComplete 会间接触发一次滚动，但 ask_user 卡片写入先于 done、且依赖 status 变化属于间接兜底，契约上不应依赖；多轮同气泡场景同理存在感知延迟）
- 根因说明：HITL 卡片数据（askUserData/askUserHistory）的写入不在自动滚动监听范围内，卡片出现时缺少确定的滚动触发源。

## 修复方案
- 修改点说明：`MessageList.vue` 新增第三个 watch——监听 HITL 卡片数据指纹（形态 kind + 问题文本/工具名 + askUserHistory 条数），指纹变化即 scrollToBottom：
  - 覆盖首次触发（ask_user / tool_confirm）、多轮同气泡镜像更新与历史增长；
  - 用户回答（answer）与决策（approved）写入不改变指纹，卡片锁定回看时不产生多余滚动（此后由恢复流的 token 变化驱动滚动）。
- 影响评估：纯增量 watch，不改变既有两个滚动 watch 行为；无后端改动、无协议改动。
- 风险点：极端场景下同一问题文本 + 同一工具名 + 同一历史条数的连续两次交互不会被滚动（指纹未变）——实际流程中每次交互问题/工具名或历史条数至少一项变化，风险可忽略。
- 回滚方案：删除新增 watch 块即可。
