# BUG 修复报告

## 基本信息
- 日期：2026-08-11
- 报告人：AI Agent
- 模块/功能：任务拆解模式（Bug1）+ 深度思考模式（Bug2）
- 严重级别：高
- 影响范围：
  - Bug1：任务拆解模式，SSE 超时或客户端断开后流程卡死，无法继续推进
  - Bug2：深度思考模式，前端流式输出完全失效，所有内容一次性出现
  - 严重级别依据：Bug1 阻断用户使用任务拆解模式（必现，当任务复杂耗时超过 5 分钟或客户端断开时）；Bug2 阻断用户使用深度思考模式的流式体验（必现，所有深度思考模式对话均受影响）

## 问题描述
- 期望结果：
  - Bug1：任务拆解模式下，即使 SSE 连接超时或客户端断开，后端异步线程应优雅停止，不持续向已完成的 emitter 发送事件
  - Bug2：深度思考模式下，前端页面应实时流式显示推理过程（reasoning）和 ReAct 思考过程（thought），而非等待全部完成后一次性显示
- 实际结果：
  - Bug1：任务拆解模式下，SSE 连接超时或客户端断开后，后端异步线程继续执行 ReAct 循环，持续向已 complete 的 emitter 发送 task_token 事件，抛出 `IllegalStateException: ResponseBodyEmitter has already completed` 异常，日志刷屏，流程卡死
  - Bug2：深度思考模式下，前端页面长时间无任何流式输出，直到后端 ReAct 循环全部完成后，所有 SSE 事件（reasoning、thought、final-answer 等）一次性到达前端

## 定位过程

### Bug1 定位过程
- 关键线索：异常信息 `SSE 发送失败: event=task_token, reason=ResponseBodyEmitter has already completed`
- 排查路径：
  1. Grep 搜索"SSE 发送失败"定位到 [AgentController.java](file:///d:/project_demo/agent_demo/agent-demo-web/src/main/java/com/agentdemo/web/controller/AgentController.java) 第 318-326 行 `sendEvent` 方法，确认异常被 catch 仅输出 WARN 日志
  2. 分析任务拆解分支（第 170-234 行）：使用 `CompletableFuture.runAsync()` 异步执行 `TaskBreakdownStream.start()`，emitter 在 `onComplete`/`onError` 回调中 complete
  3. 发现关键缺陷：没有注册 `emitter.onTimeout()` 和 `emitter.onError()` 回调；`TaskBreakdownStream` 没有 cancel 机制
  4. 确认根因：当 emitter 超时（5 分钟）或客户端断开时，Spring 自动 complete emitter，但异步线程继续执行 ReAct 循环，持续调用 `sendEvent` 向已 complete 的 emitter 发送事件

- 根因说明：**异步线程与 emitter 生命周期脱节**。任务拆解模式通过 `CompletableFuture.runAsync()` 在 ForkJoinPool 异步线程中执行三阶段编排，但没有任何机制在 emitter 超时/断开时通知异步线程停止。异步线程持续向已 complete 的 emitter 发送事件，导致 `IllegalStateException`。`sendEvent` catch 异常后仅输出 WARN 不停止，导致后续每次 `onTaskToken` 回调都重复抛异常和输出日志。

### Bug2 定位过程
- 关键线索：深度思考模式下前端流式输出失效，所有内容一次性出现
- 排查路径：
  1. 分析 [AgentController.java](file:///d:/project_demo/agent_demo/agent-demo-web/src/main/java/com/agentdemo/web/controller/AgentController.java) 深度思考分支（第 240-269 行）：`.start()` 在第 269 行**同步阻塞**执行
  2. 分析 [ReActThinkingStream.java](file:///d:/project_demo/agent_demo/agent-demo-agent/src/main/java/com/agentdemo/agent/single/ReActThinkingStream.java) 的 `start()` 方法：内部调用 `runReActLoop()`，这是一个同步 while 循环，阻塞当前线程
  3. 对比普通模式：`TokenStream.start()` 是 LangChain4j 异步实现，立即返回，Controller 立即返回 emitter，Spring 初始化 handler 后异步线程的 `sendEvent` 能实时推送
  4. 对比任务拆解模式：已使用 `CompletableFuture.runAsync()` 异步执行（2026-07-24 BUG 修复），SSE 事件实时推送正常
  5. 确认根因：深度思考模式的 `.start()` 同步阻塞 Controller 线程，Spring SseEmitter handler 未初始化，所有 `send()` 数据被缓存到 `earlySendAttempts`，Controller 返回后一次性发送

- 根因说明：**同步阻塞导致 SSE 事件全量缓存**。`ReActThinkingStream.start()` 在 Controller 请求线程中同步阻塞执行整个 ReAct 循环（可能持续数十秒），期间所有 `emitter.send()` 调用的数据被 Spring 缓存到 `earlySendAttempts` 集合（因为 Controller 方法尚未返回，SseEmitter handler 未初始化）。`start()` 完成后 Controller 返回 emitter，Spring 才初始化 handler 并一次性发送全部缓存数据，导致前端收到的所有 SSE 事件（reasoning、thought、final-answer）都是一次性到达而非实时流式。

- 历史关联：2026-07-24 的 BUG 修复文档（`docs/BUG修复文档/20260724-1028-任务拆解SSE事件非实时推送.md`）已明确记录此遗留问题："深度思考模式的 ReActThinkingStream.start() 同样是同步阻塞执行，可能存在相同的 SSE 事件延迟问题。建议后续评估是否需要同步修复"。本次修复即为该遗留问题的解决。

## 修复方案

### Bug1 修复方案
- 修改点说明：
  1. `TaskBreakdownStream` 新增 `volatile boolean cancelled` 标志位和 `cancel()` 方法，在关键检查点（Phase 2 入口、每个子任务 for 循环入口、ReAct while 循环入口、Phase 3 入口）检查 `cancelled` 标志位
  2. `AgentController` 任务拆解分支：将 `TaskBreakdownStream` 创建提取到 `CompletableFuture.runAsync()` 外部保存引用，注册 `emitter.onTimeout()` 和 `emitter.onError()` 回调，回调中调用 `breakdownStream.cancel()`
- 影响评估：仅影响任务拆解模式的异步执行流程，不影响普通模式和深度思考模式的已有逻辑
- 风险点：cancel 检查点在 LLM 调用之间，正在进行的 LLM 调用无法中途打断（需等当前 LLM 调用返回后才会检查 cancelled），但这是可接受的（单次 LLM 调用通常数秒完成）
- 回滚方案：移除 `TaskBreakdownStream.cancel()` 方法和所有 `cancelled` 检查点，移除 `AgentController` 中的 `emitter.onTimeout()`/`emitter.onError()` 回调

### Bug2 修复方案
- 修改点说明：
  1. `ThinkingTokenStream` 接口新增 `default void cancel() {}` 默认方法（不影响其他实现类）
  2. `ReActThinkingStream` 覆盖 `cancel()` 方法，新增 `volatile boolean cancelled` 标志位，在 ReAct while 循环入口和强制总结前检查 `cancelled`
  3. `AgentController` 深度思考分支：从同步 `.start()` 改为 `CompletableFuture.runAsync(thinkingStream::start)` 异步执行，注册 `emitter.onTimeout()` 和 `emitter.onError()` 回调
- 影响评估：影响深度思考模式的执行方式（同步改异步），但行为一致（回调注册方式不变），与任务拆解模式对齐
- 风险点：深度思考模式改为异步后，`emitter.onTimeout()`/`emitter.onError()` 回调中的 `thinkingStream.cancel()` 依赖 `ReActThinkingStream` 的 cancel 检查点及时响应
- 回滚方案：将深度思考分支改回同步 `.start()` 执行，移除 `ReActThinkingStream.cancel()` 方法和 `cancelled` 检查点，移除 `ThinkingTokenStream` 接口的 `default cancel()` 方法

## 遗留问题/后续动作
1. **Bug2 的 RC-2/RC-3 未修复**：深度思考模式下 ReAct 模式不发 `token` 事件（LLM content 被路由为 `thought` 事件），主回复区仅在 `final-answer` 事件时一次性显示。这是产品设计决策（ReAct 模式将内容显示在思考区），非 BUG。如需主回复区逐字流式，需评估是否在 ReAct 模式下同时发送 `token` 事件
2. **普通模式未注册 emitter 回调**：普通模式（enableThinking=false）的 `TokenStream.start()` 是 LangChain4j 异步实现，emitter 超时/断开后异步线程也可能继续运行。但普通模式通常耗时短，超时风险低。如需彻底防护，可后续为普通模式也注册 emitter 回调（但 `TokenStream` 是 LangChain4j 接口，不支持 cancel）
