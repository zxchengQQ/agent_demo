# BUG 修复报告

## 基本信息
- 日期：2026-07-23
- 报告人：AI Agent（bugfix-workflow）
- 模块/功能：深度思考 ReAct 模式 - tool_calls 流式解析与工具调用循环
- 严重级别：高
- 影响范围：所有使用深度思考模式（enableThinking=true）发送超出工具能力范围问题（如天气查询）的用户
  - 严重级别依据：阻断级（死循环消耗大量 API 额度和时间，最终强制总结的回答质量差），但仅影响深度思考模式

## 问题描述
- 期望结果：深度思考 ReAct 模式下，当用户问题超出已有工具能力范围（如"查看深圳天气"），LLM 应直接基于自身知识回答或告知用户该功能暂不支持，不陷入死循环
- 实际结果：发送"查看一下今天深圳的天气"时，ReAct 循环陷入死循环，产生 318 次碎片化的工具调用（action/observation 事件），iteration 达到 9（8轮+强制总结），大量返回"工具不存在"和"工具执行失败: URL 不能为空"，最终仅给出低质量的强制总结回答

## 复现步骤（必须可复现）
1) 启动后端服务（端口 8080）
2) 通过 API 发送请求：POST http://localhost:8080/api/agent/chat/stream，请求体 `{"message":"查看一下今天深圳的天气","enableThinking":true}`（Content-Type: application/json; charset=utf-8）
3) 观察 SSE 响应事件流

**修复前现象**：
- 响应大小 69493 字符
- 318 个 action 事件 + 318 个 observation 事件
- max iteration 9（8轮 ReAct + 1 次强制总结）
- observation 内容大量为"工具不存在: "（空工具名）和"工具执行失败: URL 不能为空"
- action 事件显示 tool_calls 被碎片化：toolName 为空，arguments 为单 token 片段（如 "http"、"://"、"wt"）

**修复后现象**：
- 响应大小 10217 字符（降低 85%）
- 0 个 action 事件 + 0 个 observation 事件
- max iteration 1（1 轮直接给出最终回答）
- LLM 遵守系统提示词约束，未编造工具名，直接基于知识回答

## 定位过程
- 关键线索：action 事件的 toolName 为空、arguments 为单 token 片段
- 排查路径：
  1. 分析 SSE 响应，发现 318 次碎片化工具调用，toolName 为空导致"工具不存在"
  2. 阅读 [ArkThinkingStreamingChatModel.parseSseLine()](file:///d:/project_demo/agent_demo/agent-demo-llm/src/main/java/com/agentdemo/llm/factory/ArkThinkingStreamingChatModel.java#L190)，发现 tool_calls delta 每个chunk 被当作独立 ToolCall 创建并直接回调 handler.onToolCalls
  3. 确认 OpenAI 协议中 tool_calls 是流式分片返回的：首个 chunk 含 id+name，后续 chunk 只有 arguments 片段
  4. 阅读 [ReActThinkingStream.executeToolCalls()](file:///d:/project_demo/agent_demo/agent-demo-agent/src/main/java/com/agentdemo/agent/single/ReActThinkingStream.java#L250)，确认每个碎片 ToolCall 都被执行（调用 ToolExecutor），导致 318 次无效调用
  5. 阅读 [ToolExecutor.execute()](file:///d:/project_demo/agent_demo/agent-demo-tools/src/main/java/com/agentdemo/tools/registry/ToolExecutor.java#L41)，确认工具不存在时只返回"工具不存在: xxx"，未告知可用工具列表
  6. 阅读 [AgentConfig.thinkingReactSystemPrompt](file:///d:/project_demo/agent_demo/agent-demo-agent/src/main/java/com/agentdemo/agent/config/AgentConfig.java#L70)，确认提示词缺乏"只用提供的工具、超出能力范围直接回答"的约束

- 根因说明（四层）：
  1. **核心根因**：`parseSseLine` 未按 index 累积 tool_calls delta，每个 SSE chunk 的 tool_calls 被当作独立 ToolCall 创建并执行，导致碎片化
  2. **Prompt 约束不足**：`thinkingReactSystemPrompt` 说"当问题需要实时信息时请主动调用工具"，但没约束"只能用提供的工具、超出能力范围直接回答"
  3. **Observation 信息不足**：工具不存在时只返回"工具不存在: xxx"，未告知可用工具列表，LLM 无法自我纠正
  4. **缺乏中断机制**：连续工具失败时无提前终止，只能空转到 maxIterations

## 修复方案
- 修改点说明（四层修复）：
  1. **核心修复**：`parseSseLine` 增加 `Map<Integer, ToolCall>` 累积器参数，按 index 累积 tool_calls delta（id/name 仅首次设置，arguments 追加拼接），在 finish_reason 时统一回调 handler.onToolCalls
  2. **Prompt 约束**：`thinkingReactSystemPrompt` 增加三条约束（只用提供的工具不编造工具名、超出能力范围直接回答、工具失败不盲目重试），并在工具描述中加入实际方法名
  3. **Observation 增强**：`ToolExecutor` 工具不存在时返回"工具不存在: xxx。可用工具: [列表]"
  4. **中断机制**：`ReActThinkingStream` 增加 `consecutiveToolFailures` 计数器，连续 3 轮工具失败时提前中断循环
- 影响评估：仅影响深度思考 ReAct 模式（chatThinkingReActStream），正常模式（chat/chatStream）和非 ReAct 思考模式（chatThinkingStream）不受影响
- 风险点：parseSseLine 签名变更（增加参数），需同步更新调用方和测试
- 回滚方案：git revert 本次提交

## 遗留问题/后续动作
- LLM 行为具有随机性，不同模型/不同时刻可能仍有尝试调用工具的情况，但连续失败中断机制（3 次阈值）可兜底
- `thinkingReactSystemPrompt` 中工具描述仍为硬编码文字，若未来新增工具需同步更新提示词（可考虑动态生成工具描述）
- SSE 响应的中文编码在 PowerShell 测试中显示乱码，但前端浏览器中正常显示（UTF-8）
