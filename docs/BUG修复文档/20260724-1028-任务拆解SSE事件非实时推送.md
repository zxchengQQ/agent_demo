## 基本信息
- 日期：2026-07-24
- 报告人：AI Agent
- 模块/功能：任务拆解模式（CR-002）/ SSE 流式推送
- 严重级别：高
- 影响范围：所有使用"任务拆解"模式的用户，在全部子任务执行完毕前无法看到任何拆解进度
 - 严重级别依据（是否阻断/可绕过/影响用户数）：功能体验阻断，无法绕过；影响所有开启任务拆解模式的用户；任务拆解涉及多轮 LLM 调用（规划+各子任务+总结），耗时可达数十秒至数分钟，期间页面完全无反馈

## 定位过程
- 关键线索：用户报告"只有到了任务全部执行结束才能知道拆解了哪些任务"，说明 SSE 事件未实时推送，而是被缓存后一次性发送
- 排查路径：
  1. 检查前端 SSE 解析逻辑（api/chat.ts）：handleSseEvent() 逐行解析 SSE 流，每个事件立即调用对应回调，逻辑正确
  2. 检查前端状态管理（stores/session.ts）：initSubTasks/updateSubTaskStatus 等方法实时更新状态并触发 Vue 响应式渲染，逻辑正确
  3. 检查后端 Controller（AgentController.java L148-194）：任务拆解分支中，每个回调通过 sendEvent(emitter, ...) 推送 SSE 事件，逻辑正确
  4. 检查 TaskBreakdownStream.start()（L187-233）：发现 start() 方法注释明确写着"同步执行规划 -> 执行 -> 总结三阶段"，在 Controller 请求线程中同步阻塞执行
  5. 分析 Spring SseEmitter 工作原理：SseEmitter.send() 在 Controller 方法返回前，因 handler 未初始化，数据被缓存到 earlySendAttempts 集合；Controller 方法返回后 Spring 调用 initialize() 设置 handler 并一次性发送缓存数据
- 根因说明：TaskBreakdownStream.start() 在 Controller 请求线程中同步阻塞执行，导致 Controller 方法无法及时返回 SseEmitter。Spring SseEmitter 在 Controller 方法返回前无法初始化 handler，所有 emitter.send() 的数据被缓存到 earlySendAttempts，直到 start() 执行完毕、Controller 方法返回后，Spring 才将缓存数据一次性发送给客户端，导致 SSE 事件无法实时推送

## 修复方案
- 修改点说明：将 AgentController 中任务拆解分支的 start() 调用从同步执行改为异步执行（CompletableFuture.runAsync），使 Controller 方法立即返回 SseEmitter，Spring 得以及时初始化 handler，后续 emitter.send() 调用可实时将数据推送到客户端
- 影响评估：仅影响任务拆解分支（enableTaskBreakdown=true），不影响深度思考模式和原路径
- 风险点：
  1. 异步线程中执行 start()，需确保 SseEmitter 线程安全（SseEmitter.send() 内部 synchronized，线程安全有保障）
  2. CompletableFuture.runAsync 使用 ForkJoinPool.commonPool()，长耗时任务可能占用公共线程池资源（当前可接受，后续可引入专用线程池优化）
  3. 异步线程中的异常已由 TaskBreakdownStream.start() 内部的 try-catch + onError 回调处理，不会丢失
- 回滚方案：将 CompletableFuture.runAsync(() -> ...) 包装移除，恢复为同步调用 planAgent.chatTaskBreakdownStream(...).start()

## 遗留问题/后续动作
- 深度思考模式（enableThinking=true）的 ReActThinkingStream.start() 同样是同步阻塞执行，可能存在相同的 SSE 事件延迟问题。由于深度思考模式通常只有单轮 LLM 调用 + 少量 ReAct 迭代，耗时较短，延迟不明显。建议后续评估是否需要同步修复
