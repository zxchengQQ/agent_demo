# BUG 修复报告

## 基本信息
- 日期：2026-08-21
- 报告人：AI Agent（bugfix-workflow）
- 模块/功能：前端对话模块 - HITL 人机交互（ask_user 事件 → ConfirmCard 选项框渲染）
- 严重级别：高
- 影响范围：所有开启"🤝 人机交互"开关并使用 confirm 类型提问（关键操作确认）的用户
  - 严重级别依据：阻断 HITL 核心交互闭环（用户无法点击选项，Agent 无法恢复执行），直接影响本次 HITL 功能交付

## 问题描述
- 期望结果：Agent 发起 confirm 类型提问时，前端将选项渲染为可点击的选项框（按钮），用户点击选项后自动回复并恢复 Agent 执行
- 实际结果：选项框（ConfirmCard）虽然渲染出按钮，但按钮全部处于 disabled 禁用状态，用户无法点击；同时输入框不进入"请回复上方问题..."等待态，交互链路整体失效

## 复现步骤（必须可复现）
1) 启动后端（8080）与前端（5173）
2) 打开对话页面，点击"🤝 人机交互"开关开启 HITL
3) 输入"删除文件 test.txt"并发送（触发 confirm 类型关键操作确认）
4) 观察助手消息下方的确认卡片

**修复前现象**：
- 确认卡片显示问题文本"确认删除文件 test.txt？此操作不可恢复。"及按钮"确认删除"/"取消"
- 但按钮均带 `disabled` 属性（灰显），点击无任何反应
- 输入框 placeholder 仍为"输入消息，Enter 发送，Shift+Enter 换行"（未显示等待回复提示）

**修复后现象**：
- 按钮可正常点击（`disabled: [false, false]`）
- 点击"确认删除"后确认卡片移除，选中值作为用户消息发送，后端恢复执行并产出最终回答

## 定位过程
- 关键线索：浏览器复现发现 `.confirm-option` 按钮存在但均带 `disabled` 属性
- 排查路径：
  1. 浏览器端到端复现：发送"删除文件 test.txt"，通过 evaluate 检查 DOM，确认 ConfirmCard 渲染 2 个按钮但 `disabled=[true, true]`
  2. 阅读 [MessageItem.vue](file:///d:/project_demo/agent_demo/agent-demo-frontend/src/components/MessageItem.vue#L379-L386)：ConfirmCard 绑定 `:disabled="props.message.status !== 'incomplete'"`
  3. 阅读 [AgentController.java](file:///d:/project_demo/agent_demo/agent-demo-web/src/main/java/com/agentdemo/web/controller/AgentController.java#L357-L362)：`onAskUser` 回调发送 `ask_user` 事件后**立即发送 `done` 事件并 `emitter.complete()`**
  4. 阅读 [ChatWindow.vue](file:///d:/project_demo/agent_demo/agent-demo-frontend/src/components/ChatWindow.vue#L210-L220)：`onDone` 回调调用 `store.markComplete(assistantMsgId)`，消息 status 变为 `complete`
  5. 阅读 [session.ts](file:///d:/project_demo/agent_demo/agent-demo-frontend/src/stores/session.ts#L58-L64)：`isWaitingForUserInput` getter 要求 `status === 'incomplete'`，因 status 已为 complete 而返回 false
- 根因说明：**事件时序导致的状态依赖错误**。ask_user 事件后后端立即发送 done，前端 markComplete 将消息 status 置为 complete。而 ConfirmCard 的 `disabled` 绑定 `status !== 'incomplete'`，isWaitingForUserInput 也要求 `status === 'incomplete'`，二者均基于"流式进行中"的状态语义判断。但在 HITL 场景下，status=complete（SSE 流结束）恰恰是"等待用户输入"的开始，语义不匹配导致按钮禁用、等待态失效

## 修复方案
- 修改点说明：HITL 等待用户输入的核心状态应由 **askUserData 是否存在** 决定，而非消息 status（status 仅表示 SSE 流是否结束）
  1. `session.ts` `isWaitingForUserInput`：去掉 `lastMsg.status === 'incomplete'` 条件，改为 `!!lastMsg.askUserData`
  2. `MessageItem.vue` ConfirmCard `:disabled`：由 `status !== 'incomplete'` 改为恒 `false`，askUserData 存在期间始终可交互；防重复点击由 ConfirmCard 内部 `isSelected` 锁定（点击后即禁用）
- 影响评估：仅影响 HITL confirm 卡片渲染与等待态判断；text 类型（文本展示）、非 HITL 路径零回归
- 风险点：无显著风险。用户回复后 `clearAskUser` 会清除 askUserData 并标记 complete，卡片随之移除，不会出现重复可点击的残留
- 回滚方案：将 `session.ts` getter 恢复 `&& lastMsg.status === 'incomplete'`，`MessageItem.vue` 恢复 `:disabled="props.message.status !== 'incomplete'"` 即可
