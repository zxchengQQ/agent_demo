# BUG 修复报告

## 基本信息
- 日期：2026-08-24 21:40
- 报告人：AI 辅助修复（bugfix-workflow）
- 模块/功能：工具权限控制——ask 级工具确认卡片批准/拒绝流程（Task-17 前端联动）
- 严重级别：高
- 影响范围：所有 ask 级工具（httpGet/httpPost/MCP 工具等）的确认卡片"批准/拒绝"按钮——点击后无任何反应，页面永久停留在"生成中"，用户被迫刷新页面，会话流程完全阻断
 - 严重级别依据：ask 级工具为权限管控核心交互（AC-N03/AC-S02 全链路），点击批准 100% 触发卡死，无法绕过（输入框发文字会被解释为"拒绝"），属功能完全阻断

## 问题描述
- 期望结果：点击确认卡片"批准"按钮后，前端携带 `toolApproved=true` 发起流式恢复请求，后端执行被拦截的工具并续跑 ReAct 循环，最终输出结果、页面恢复正常。
- 实际结果：点击"批准"按钮后无任何网络请求发出，页面卡在"生成中"，后端无后续日志（第一次 SSE 流因 pending 挂起保持打开，前端 `isStreaming` 永远为 true）。

## 复现步骤（必须可复现）
1) 启动后端（`start.ps1 -Provider bailian`）与前端（`npm run dev`），配置 LLM 模型
2) 进入对话页，在工具选择器勾选 ask 级工具 `httpGet`，发送消息："用 httpGet 工具获取 https://example.com 网页的标题并告诉我，这是一步就能完成的简单任务，不要拆解"
3) 等待 Agent 调用 httpGet，页面弹出权限确认卡片（工具名/描述/参数摘要/批准/拒绝按钮）
4) 点击"批准"按钮
5) 观察：页面卡在"生成中"，Network 面板无新请求，后端日志无任何新增——流程卡死

复现验证（API 层）：步骤 3 之后直接 POST `/api/agent/chat/stream`，body 为 `{"sessionId":"...","message":"","toolApproved":true}`（即修复前按钮实际会构造的请求体），后端返回 **400 "消息内容不能为空"**（`@NotBlank` 校验拒绝）。

## 定位过程
- 关键线索：用户后端日志显示恢复请求 `approved=null`（而非 true），且恢复续跑后 LLM 二次调用 httpGet 再次暂停（retryCount=1）后日志中断
- 排查路径：
  1. 日志 `Agent 统一模式恢复: approved=null` → 说明点击按钮的请求要么没带 `toolApproved=true`，要么根本不是按钮发出的（后经分析确认：该日志来自用户后续在输入框输入文字触发的恢复，`toolApproved=null` 按设计走"拒绝"分支，LLM 换方案时再次调用 httpGet 形成二次暂停——此为正常设计行为，非卡死主因）
  2. 追踪按钮链路：`ConfirmCard @approve` → `MessageItem` → `MessageList` → `ChatWindow.handleApprove()` → `sendMessage('', true)`
  3. 发现 `sendMessage` 第一行 `if (!message.trim()) return;`——**空消息直接拦截，请求根本不发**，与"后端无任何日志"现象完全吻合
  4. 进一步验证：即使绕过前端拦截，`ChatRequest.message` 的 `@NotBlank` 校验也会返回 400（API 实测复现），形成双重拦截
- 根因说明：`handleApprove`/`handleDeny` 调用 `sendMessage('', true/false)` 传入空 message。空串被前端 `sendMessage` 的空消息拦截（AC-014）直接 return，请求未发出；第一次 SSE 流因 `tool_confirm` pending 挂起保持打开，前端停留在流式生成状态，页面永久卡死。这是 Task-17 实现时的疏漏——此前 AC-N03 端到端验收使用 PowerShell 模拟客户端（携带了非空 message），未覆盖真实 UI 按钮路径。

## 修复方案
- 修改点说明：`handleApprove`/`handleDeny` 不再传空 message，改为携带非空决策文案（"已批准使用工具"/"已拒绝使用工具"），同时通过前端空消息拦截与后端 `@NotBlank` 校验。该文案仅作 UI 展示气泡，后端 `resumeToolConfirm` 恢复路径不将其写入推理上下文（技术方案 §3.4：权限决策由 `toolApproved` 表达），无逻辑副作用。
- 影响评估：仅影响确认卡片批准/拒绝两个按钮的触发路径，普通消息发送、askUser HITL 恢复路径零变更。
- 风险点：极低。决策文案会作为用户消息气泡显示在会话中（属预期 UI 行为，与 askUser 卡片回答展示一致）。
- 回滚方案：还原 `ChatWindow.vue` 中两个函数的 message 参数为 `''` 即可（git revert 单文件改动）。
