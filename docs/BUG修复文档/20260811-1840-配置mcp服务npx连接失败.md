# BUG 修复报告

## 基本信息
- 日期：2026-08-11 18:40
- 报告人：AI Assistant
- 模块/功能：agent-demo-mcp（MCP 服务管理 - stdio 传输连接）
- 严重级别（低/中/高）：高
- 影响范围：所有通过页面/JSON 配置使用 `npx`/`node` 等裸命令作为 stdio MCP Server 的用户
- 严重级别依据：阻断 stdio 类型 MCP Server 接入（如 fetch），且用户用业界标准 `npx` 配置必然失败，无法绕过

## 问题描述
- 期望结果：前端页面通过 JSON 配置 `{"mcpServers": {"fetch": {"command": "npx", "args": ["mcp-fetch-server"]}}}` 添加 stdio MCP Server 应连接成功
- 实际结果：后端返回 5400（MCP_CONNECTION_FAILED），错误 `message=连接 MCP Server 失败: fetch`，连接失败

## 复现步骤（必须可复现）
1) 启动后端应用（agent-demo-bootstrap，端口 8080）
2) 在前端「设置 → MCP 服务」页面粘贴 JSON 配置：`{"mcpServers": {"fetch": {"command": "npx", "args": ["mcp-fetch-server"]}}}`
3) 点击「保存配置」提交添加
4) 观察后端返回 5400 连接失败（日志：`业务异常: code=5400, message=连接 MCP Server 失败: fetch`）

## 复现环境
- 设备/系统：Windows（Java 17.0.7）
- 应用版本/配置：agent-demo 1.0.0，`command: "npx"`（stdio 传输）
- 相关依赖或外部条件：Node.js/npx 已安装（npx 解析为 `npx.ps1`/`npx.cmd`）

## 定位过程
- 关键线索：静态配置的 fetch（`command: npx.cmd`）连接成功，但动态配置的 fetch（`command: npx`）连接失败
- 排查路径：
  1) 用 `Get-Command npx` 确认 Windows 下 `npx` 解析为 `npx.ps1`（PowerShell 脚本）
  2) 分析 `McpTransportFactory.createStdioTransport()`：直接用 `config.getCommand()`（npx）传给 `StdioMcpTransport.Builder.command()`
  3) 确认 LangChain4j 的 `StdioMcpTransport` 内部用 `ProcessBuilder` 启动命令，Windows 的 `CreateProcess` 无法直接执行无扩展名的裸命令（`npx` 实为 `npx.ps1`/`npx.cmd`），导致子进程启动失败
- 根因说明：**Windows 下 Java `ProcessBuilder` 无法直接执行无扩展名的命令**。用户按业界标准（Claude Desktop / Cursor）配置 `npx`，但 Windows 上必须用 `npx.cmd`。系统未做适配，也未在错误提示中暴露根因（仅笼统返回"连接失败"）

## 修复方案
- 修改点说明：
  1. **命令适配**（核心）：`McpTransportFactory` 新增 `resolveWindowsCommand()`，在 Windows 下若 command 为无扩展名裸命令且 PATH 中存在对应的 `.cmd`/`.bat`/`.exe` 文件，自动补全扩展名（`npx` → `npx.cmd`）。`createStdioTransport()` 接入适配后的命令。
  2. **错误提示增强**（辅助）：`McpServerManager.connect()` 连接失败时，错误消息包含底层根因（`rootCauseMessage()` 提取异常链最深层 cause），让用户定位配置问题。
- 影响评估：仅影响 stdio 传输的命令解析；非 Windows 平台和已带扩展名命令不受影响
- 风险点：若 PATH 中存在同名 `.cmd` 和 `.exe`，优先用 `.cmd`；`command` 为带路径的绝对命令（含 `.`）不触发适配
- 回滚方案：移除 `resolveWindowsCommand` 调用与 `rootCauseMessage` 逻辑即可还原
